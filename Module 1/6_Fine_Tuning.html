Section 01

The Adaptation Spectrum

A foundation model (Module 5, §07) is generic. Getting it to do your task well is "adaptation" — and there isn't one way to do it. There's a spectrum, trading off cost, data requirements, and how deeply the model's behavior actually changes.

FIG 1 — The adaptation spectrum. Modules 5 covered the far right (foundation-model pretraining). This module lives in the middle three: in-context learning, PEFT/LoRA, and full fine-tuning.
Method Weights change? Data needed Compute needed Best when
Zero/Few-shot prompting No 0–10 examples, written into the prompt Inference only Task is close to what the base model already does well
PEFT (LoRA, etc.) Small adapter only (<1%) Hundreds–thousands of labeled examples 1 GPU, hours (or CPU, much slower — §07) Task-specific behavior change, limited hardware/data
Full fine-tuning All parameters Thousands–millions of examples Multiple GPUs, hours–days Large budget, deep/broad behavior change needed
The question that decides where you sit on this spectrum: "Can I describe the task well enough in a prompt, or does the model need to actually change?" If a well-written prompt with a few examples gets acceptable quality, stop there — it's free and instant. Only pay the cost of fine-tuning when prompting demonstrably can't get you the reliability, format-consistency, or domain depth you need.
Section 02

In-Context Learning (ICL)

In-context learning is the striking observation that a large enough pretrained LLM can pick up a new task just from examples placed in the prompt — with zero gradient updates. The "learning" happens entirely within a single forward pass, at inference time.

FIG 2 — A few-shot prompt: instruction + K labeled examples + the new query. All of it is one input sequence — the model was never trained on this specific task, it infers the pattern purely from what's in context.

The ICL family

Variant What's in the prompt Trade-off
Zero-shot Just the instruction, no examples Cheapest, but relies entirely on the base model already understanding the task
Few-shot Instruction + K example input→output pairs Better reliability and format-following; costs prompt-length tokens on every call
Chain-of-thought (CoT) Examples show step-by-step reasoning before the final answer Meaningfully improves multi-step reasoning tasks; increases output length/cost

Why does this even work? (open research question, current best explanation)

The leading hypothesis: during pretraining on trillions of tokens, the model repeatedly encounters implicit "pattern-completion" structures (FAQs, tables, structured documents, code with examples). Next-token prediction on that data implicitly trains a general skill: "infer the pattern governing this sequence and continue it." A few-shot prompt is just a novel instance of exactly that skill — the model isn't learning a new task from scratch, it's recognizing "oh, this is a pattern-completion problem" and applying an already-general capability.

Limits of ICL

✗

Doesn't persist

Nothing is learned permanently — every single call must re-supply the examples in the prompt.

✗

Context-length cost

More/longer examples = more tokens billed and processed on every single inference call.

✗

Ceiling on task depth

Deep domain adaptation (new vocabulary, subtle stylistic consistency) is hard to fully instill via a handful of examples.

✗

Sensitive to example choice/order

Which examples, and in what order, can noticeably swing output quality — a known fragility.

When these limits bite, the next step on the spectrum is to actually change the weights — which is where quantization and LoRA (§§04–05) come in.

Section 03

Full Fine-Tuning

Full fine-tuning continues training the entire pretrained model — every parameter — on a smaller, task-specific labeled dataset, using ordinary backpropagation. It's conceptually the simplest adaptation method, and the most expensive.

Why it's expensive: the memory math

// For a model with P parameters, training (not just inference!) needs to hold in memory: Model weights P × bytes_per_param // e.g. P × 2 bytes for fp16 Gradients P × bytes_per_param // same shape as weights Optimizer state (Adam: m, v) P × 2 × 4 bytes // Adam keeps 2 extra fp32 buffers per param Activations (for backprop) depends on batch size, seq length, depth // Worked example: a 7B-parameter model, fp16 weights, Adam optimizer Weights: 7B × 2 bytes = 14 GB Gradients: 7B × 2 bytes = 14 GB Adam states: 7B × 8 bytes = 56 GB ───────── Total ≈ 84 GB // before activations — already exceeds a single 80GB GPU
This is the core motivation for everything else in this module. Full fine-tuning of even a "small" 7B model needs multiple high-end GPUs. Quantization (§04) attacks the weight-memory term. LoRA (§05) attacks the gradient + optimizer-state terms, by freezing almost everything.

Other real risks of full fine-tuning

Risk What happens
Catastrophic forgetting Aggressively updating all weights on a narrow dataset can degrade general capabilities the base model had before
Overfitting on small data With only hundreds/thousands of examples but billions of parameters, the model can memorize rather than generalize
Storage cost per task Every fine-tuned variant is a full copy of the model — 10 tasks = 10 × model size on disk

These three problems — memory cost, forgetting, and per-task storage — are exactly what parameter-efficient fine-tuning (PEFT) methods, and LoRA specifically, were designed to solve.

Section 04

Quantization — Shrinking the Weight-Memory Term

Model weights are normally stored as 32-bit or 16-bit floating point numbers. Quantization represents them with far fewer bits — 8-bit or even 4-bit integers — trading a small amount of numerical precision for a large reduction in memory and (often) faster inference.

FIG 3 — Halving the bit-width roughly halves memory. INT4 fits a 7B model in under 4GB — small enough for a consumer laptop, or (slowly) a CPU.

The core math: scale + zero-point

// Map a real-valued weight range [min, max] onto integers [0, 2^bits − 1] scale = (max − min) / (2^bits − 1) zero_point = round(−min / scale) // Quantize: real weight → integer q = round(w / scale) + zero_point // Dequantize: integer → approximate real weight (used at inference time) ŵ = (q − zero_point) × scale // Worked example: weights range [-2.0, 2.0], 4-bit (16 levels, 0..15) scale = 4.0 / 15 = 0.267 w = 1.3 → q = round(1.3/0.267) + round(2.0/0.267) = round(4.87) + round(7.49) = 5 + 7 = 12 dequantize: ŵ = (12 − 7) × 0.267 = 1.335 // close to original 1.3, small quantization error
Method Idea Notes
Post-training quantization (PTQ) Quantize an already-trained model's weights, no retraining Fast, but accuracy loss is fixed after the fact — GPTQ, AWQ are refined PTQ algorithms
GGUF A file format (used by llama.cpp) packaging quantized weights for efficient CPU/edge inference What lets a fine-tuned model actually run fast on a laptop CPU (see companion notebook)
QLoRA Quantize the frozen base model to 4-bit, then LoRA-fine-tune on top in full precision Combines both techniques — see callout below
QLoRA — why quantization and LoRA are usually used together, not as alternatives: quantization shrinks the frozen base model's memory footprint; LoRA (§05) adds a tiny number of new, full-precision trainable parameters on top. Combined (Dettmers et al., 2023), this is what lets a 7B–13B model be fine-tuned on a single consumer GPU — or, at reduced speed, even a CPU, which is exactly the setup the companion fine-tuning notebook uses.
Section 05

LoRA — Low-Rank Adaptation

LoRA (Hu et al., 2021) is the single most widely used PEFT method. The insight: you don't need to update a full weight matrix to adapt it — a very low-rank update is usually enough to steer behavior on a new task.

FIG 4 — LoRA decomposes the weight update ΔW into two small matrices B (d×r) and A (r×d), whose product BA approximates a full d×d update at a fraction of the parameters. W itself never changes.

The math

// Standard forward pass through a linear layer h = W · x // W is d_out × d_in, frozen, pretrained // LoRA adds a parallel low-rank path h = W · x + (α/r) · B · A · x // B: d_out × r, A: r × d_in, r ≪ d_out, d_in // A is initialized random-small, B initialized to ZERO // → at the start of training, BA = 0, so the model behaves EXACTLY like the base model // → training then gradually learns a small, targeted correction // α (alpha) is a fixed scaling factor — controls how much the LoRA update contributes // higher α/r → stronger adaptation, at more risk of overfitting/forgetting

Worked example: parameter count at real scale

Full fine-tuning LoRA (r=8)
Trainable parameters (7B model, all attention projections) 7,000,000,000 ≈ 4,000,000
% of total model 100% ≈ 0.06%
Optimizer state (Adam, fp32) 56 GB ≈ 32 MB
Checkpoint size to store per task ~14 GB (fp16 full model) ~8–16 MB (adapter only)
Why does training only ~0.06% of the parameters still work well? The hypothesis behind LoRA (supported by prior work on the "intrinsic dimensionality" of fine-tuning) is that the change a downstream task requires — as opposed to the full knowledge the model already has — lives in a low-dimensional subspace. You don't need to re-teach the model language; you need to nudge it, and that nudge has low intrinsic rank.
Exam favourite: "Why is B initialized to zero and A initialized randomly, not the other way around, and not both zero?" — Both zero means the gradient through BA is zero everywhere (dead layer, never learns). Both random means training starts from a random, non-zero perturbation of a working pretrained model — degrading it immediately. B=0, A=random gives BA=0 at init (identical to the base model) while still allowing a non-zero gradient to flow into A immediately, so learning starts cleanly from the base model's exact behavior.
Section 06

The PEFT Ecosystem

LoRA is the most popular parameter-efficient fine-tuning method, but not the only one. Knowing the landscape — and the one library that implements almost all of it — matters for the lab.

Method What's trained Trade-off vs. LoRA
LoRA Low-rank BA matrices injected into linear layers (usually attention projections) The default choice — good quality, simple, widely supported
QLoRA Same as LoRA, but the frozen base model is 4-bit quantized Lowest memory footprint — enables fine-tuning larger models on smaller hardware (§04)
Prefix tuning A short sequence of trainable "virtual token" vectors prepended to every layer's keys/values No architecture changes to weights at all, but historically less expressive than LoRA
Prompt tuning Trainable virtual tokens prepended only at the input embedding layer Fewest trainable parameters of all; needs a larger base model to work well
Adapters Small bottleneck feed-forward blocks inserted between existing layers Adds inference latency (extra layers in the forward path); LoRA avoids this by merging into existing weights

The table names five methods, but the thing that actually distinguishes them is where, in a single frozen transformer block, each one inserts its trainable parameters — and whether that insertion sits parallel to the frozen path (free to merge away later) or serial, in the forward path itself (a permanent extra hop). FIG 5 lines all five up against one block so the difference is visible instead of just described.

FIG 5 — All five PEFT methods placed against one frozen transformer block. Prompt tuning touches only the input, once. Prefix tuning and LoRA/QLoRA both touch every layer but stay out of the forward path (prefix adds K/V context, LoRA runs parallel and merges away). Adapters are the odd one out: they sit serially inside the forward path itself, which is the direct, visual reason they're the one method that permanently adds inference latency.
Why LoRA specifically won out in practice: because BA has the exact same shape as the frozen W, it can be merged into the base weights after training ( W' = W + BA) — meaning zero extra inference latency compared to the original model. Adapters and prefix-tuning both add a small amount of runtime cost that LoRA avoids entirely.

HuggingFace PEFT — the library that implements all of this

from peft import LoraConfig, get_peft_model, TaskType from transformers import AutoModelForSeq2SeqLM model = AutoModelForSeq2SeqLM.from_pretrained( "google/flan-t5-small") config = LoraConfig( task_type =TaskType.SEQ_2_SEQ_LM, r = 8, # rank lora_alpha = 16, # scaling: alpha/r = 2 lora_dropout = 0.05, target_modules =[ "q", "v"], # which projections get a LoRA adapter ) model = get_peft_model(model, config) model.print_trainable_parameters() # → trainable params: 344,064 || all params: 77,285,760 || trainable%: 0.445%

Three lines of actual change: load the base model as normal, wrap it in get_peft_model with a config, then train with the ordinary HuggingFace Trainer exactly as if it were full fine-tuning — PEFT handles freezing everything except the injected adapters automatically. The companion notebook uses exactly this pattern.

Section 07

The Fine-Tuning Workflow — Applied to the Lab

The lab task is: fine-tune a small LLM as a QA system. Here's the end-to-end workflow the companion notebook implements, and the decisions at each step.

1

Choose a base model

Small enough to fine-tune on CPU in reasonable time: Flan-T5-small/base (already instruction-tuned for QA-style tasks), or a 4-bit-quantized Phi/Gemma for a decoder-only alternative.

2

Prepare QA data

(context, question, answer) triples — e.g. a SQuAD-style subset — formatted as the model's expected input/output text pairs.

3

Apply LoRA

Wrap the base model with a LoraConfig targeting attention projection layers, freezing everything else (§§05–06).

4

Train

Standard supervised fine-tuning loop — cross-entropy loss on the target answer tokens, small batch size and learning rate given limited hardware.

5

Evaluate

Exact-match / F1 against held-out QA pairs, plus qualitative spot-checks on questions outside the training distribution.

6

Merge & export (optional)

W' = W + BA merged into a single deployable model — or keep the adapter separate to swap between tasks cheaply.

Key hyperparameters and what they actually control

Hyperparameter What it controls Typical starting point
r (rank) Capacity of the LoRA update — higher r can fit more complex changes, at more trainable params 4–16 for small models/tasks
lora_alpha Scaling of the LoRA contribution (effective strength = alpha/r) Often set to 2× rank
target_modules Which weight matrices get an adapter (commonly Q and V projections; sometimes all linear layers) Start with attention projections only
Learning rate Step size for the (small) set of trainable parameters Higher than full fine-tuning — often 1e-4 to 3e-4, since so few params are updated
Batch size Examples per gradient step Small (1–8) on CPU; larger with gradient accumulation to simulate bigger batches
CPU vs. GPU, honestly: LoRA fine-tuning a small model (Flan-T5-small, ~80M params) on CPU is genuinely feasible — slow (minutes per epoch on a small dataset, vs. seconds on GPU) but it completes. The companion notebook is written to run either way: it detects CUDA automatically and falls back to CPU with a smaller batch size and fewer steps, so the lab is completable without a GPU, while still being correct code that scales up immediately if a GPU becomes available.
Section 08

Key Takeaways & Exam Prep

✓

Adaptation is a spectrum

Prompting → PEFT → full fine-tuning → pretraining. Pick the cheapest method that meets the reliability bar.

✓

ICL learns nothing permanent

Few-shot examples steer one forward pass; they must be resupplied every call.

✓

Full fine-tuning's cost is dominated by optimizer state

Adam's extra buffers, not just the weights, are why a 7B model needs ~84GB to fully fine-tune.

✓

Quantization trades precision for memory

INT4 gets a 7B model under 4GB via a scale + zero-point mapping, at a small, usually-acceptable accuracy cost.

✓

LoRA freezes W, trains BA

A low-rank update (~0.06% of params) is often enough to adapt behavior — merges back with zero inference cost.

✓

QLoRA = quantize + LoRA together

4-bit frozen base + full-precision LoRA adapter is what makes single-GPU (or CPU) fine-tuning of billion-parameter models realistic.

✓

PEFT is a 3-line wrap, not a rewrite

HuggingFace's peft library wraps any model; training code is otherwise unchanged.

✓

CPU fine-tuning is slow, not impossible

Small models + LoRA make the lab completable without a GPU — the companion notebook auto-detects and adapts.

Common exam questions

Question Short answer
Why does full fine-tuning need much more memory than just storing the model weights? The optimizer (e.g. Adam) keeps extra per-parameter state (momentum + variance), and gradients must also be stored — together often 5–6× the raw weight memory
What does LoRA actually train? Two small low-rank matrices, B (d×r) and A (r×d), added to a frozen pretrained weight matrix W as W + BA
Why initialize B to zero in LoRA? So the LoRA path contributes exactly zero at the start of training — the model is identical to the base model before any adaptation happens
What is QLoRA? Quantizing the frozen base model to 4-bit while keeping the LoRA adapter in full precision — combines both techniques' memory savings
Why can a LoRA adapter be merged into the base model with zero inference cost? BA has the exact same shape as W, so W' = W + BA is computed once, offline, after training — no extra layers at inference time
What's the practical difference between few-shot prompting and fine-tuning? Prompting steers behavior temporarily, per-call, with no weight changes; fine-tuning permanently changes (some of) the model's weights, persisting across all future calls
