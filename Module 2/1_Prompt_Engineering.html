Section 01

Zero-Shot Prompting

Zero-shot prompting means asking an instruction-tuned LLM to perform a task by describing it in natural language alone — no worked examples included. It works because instruction-tuning (Module 1 §07's "adaptation" step) already exposed the model to millions of instruction→response pairs across countless task types; a new instruction at inference time is just another point in a space the model has already learned to navigate.

System: You are a helpful assistant. User: Classify the sentiment of this review as Positive, Negative, or Neutral. Review: "The battery life is incredible but the camera is disappointing." Model: Neutral — the review expresses both a strong positive (battery) and a negative (camera), balancing out overall.

When zero-shot works — and when it doesn't

Zero-shot tends to work when... Zero-shot tends to fail when...
The task is common and well-represented in pretraining/instruction data (translation, summarization, sentiment) The task requires a specific, unusual output format the model has to infer correctly on the first try
The instruction is unambiguous and self-contained The task is domain-specific with conventions the model can't guess (your company's ticket taxonomy, a niche schema)
You need speed/cost — no examples means a shorter, cheaper prompt Edge cases and boundary behavior matter and need to be demonstrated, not just described
The core trade-off across this entire section: zero-shot → few-shot → chain-of-thought → self-consistency is a ladder of increasing prompt length (and therefore cost and latency) in exchange for increasing reliability. Always start at zero-shot and climb only as far as accuracy demands — see §05 for how to decide when to stop.
Section 02

Few-Shot Prompting

Few-shot prompting adds K worked examples (input→output pairs) directly into the prompt before the real query. The model performs the task purely via in-context learning — no weight updates, exactly as introduced in Module 1 §02.

User: Classify sentiment as Positive, Negative, or Neutral. Review: "Best purchase I've made all year." → Positive Review: "Stopped working after two days." → Negative Review: "It's fine, does what it says." → Neutral Review: "Works okay I guess, nothing special." → Neutral

What actually changes with more examples

FIG 1 — The typical shape: going from 0 to a handful of examples yields the largest accuracy gain; beyond roughly 4–8 shots, returns diminish and can even reverse (context dilution, recency bias toward the last example).
Factor Why it matters
Example selection Examples close to the actual query (in topic, difficulty, format) transfer better than generic ones — this is the entire idea behind retrieval-augmented few-shot prompting
Example order LLMs show measurable sensitivity to ordering — models tend to weight the most recent example more heavily (recency bias)
Label balance An unbalanced set of examples (e.g. 3 Positive, 1 Negative) can bias the model's output distribution even when the instruction is neutral
Format consistency Every example should use the exact same input/output template — inconsistent formatting is one of the most common few-shot failure modes
Exam favourite: "Why doesn't few-shot performance keep improving as you add more examples?" — context dilution (the query gets buried among many examples), increased chance of an unhelpful or misleading example sneaking in, and the fixed context window making room for fewer, less-relevant examples as k grows.
Section 03

Chain-of-Thought (CoT) Prompting

Standard few-shot prompting shows input→output pairs. Chain-of-thought prompting shows input→ reasoning→output instead — the worked examples include the intermediate steps, not just the final answer. This alone produces large accuracy gains on multi-step tasks (arithmetic, logic, multi-hop QA).

Standard prompting

Q: Roger has 5 tennis balls. He buys 2 more cans of 3 balls each. How many does he have now?

A: 11

Chain-of-thought prompting

Q: Roger has 5 tennis balls. He buys 2 more cans of 3 balls each. How many does he have now?

A: Roger started with 5 balls. 2 cans × 3 balls = 6 more balls. 5 + 6 = 11. The answer is 11.

Zero-shot CoT: the "magic phrase"

You don't need worked examples to trigger step-by-step reasoning — appending a simple instruction is often enough (Kojima et al., 2022):

User: A juggler can juggle 16 balls. Half are golf balls, and half of the golf balls are blue. How many blue golf balls are there? Let's think step by step.
// Why this works — the leading hypothesis // Next-token prediction was trained on huge amounts of text where reasoning // IS spelled out before a conclusion (math solutions, proofs, explanations, // forum answers). "Let's think step by step" pattern-matches the model into // that distribution of text — and once it starts generating intermediate // steps, each step becomes part of the CONTEXT for predicting the next one. // The model is effectively using its own output as scratch space.
Why CoT actually improves accuracy, mechanically: a decoder-only LLM (Module 1 §05) can only do a fixed amount of "computation" per generated token — one forward pass, one shot at the next token. A hard multi-step problem solved in a single token has no room for intermediate computation. Spreading the reasoning across many generated tokens gives the model many forward passes worth of computation for one problem — each token can attend back to every prior reasoning step via self-attention.
Variant How it's triggered Best for
Few-shot CoT Worked examples include full reasoning chains Highest reliability; costs more prompt tokens
Zero-shot CoT "Let's think step by step" (or similar) appended, no examples Quick reliability boost with no example-writing effort
Auto-CoT Automatically generates and selects diverse CoT exemplars Removes manual example-writing while keeping few-shot's reliability
Section 04

Self-Consistency

A single chain-of-thought can go down a wrong reasoning path. Self-consistency (Wang et al., 2022) samples multiple independent CoT reasoning paths for the same question (using temperature > 0 for diversity), then takes a majority vote over the final answers — discarding the reasoning paths themselves.

FIG 2 — Self-consistency: sample K independent reasoning paths, keep only the final answers, and return the most frequent one. One flawed path (Path 3) gets outvoted rather than trusted.
// Self-consistency, formally answer = mode( {a₁, a₂, ..., a_K} ) // K independently sampled CoT paths, T > 0 // Cost: K× the inference cost of a single CoT call // Typical K in papers: 5–40, with accuracy gains flattening past ~20
Why voting on the ANSWER (not the reasoning) is the key design choice: reasoning paths can differ wildly in wording while converging on the same correct answer, or share superficial similarity while being wrong. Voting on the final extracted answer sidesteps having to judge reasoning quality — it only requires that correct reasoning paths are more common than any single specific wrong path, which holds empirically for most well-posed problems.
Preview — this is test-time compute scaling. Self-consistency spends more inference-time compute (K samples) to buy higher accuracy, with zero retraining. Module 2 §03 (Test-Time Scaling) generalizes this exact idea — more samples, more reasoning tokens, more inference compute — into a full framework for trading inference cost against accuracy.
Section 05

Prompt Anatomy & Best Practices

Every technique above is really one skill: structuring a prompt so the model has everything it needs, and nothing that misleads it. A reliable prompt separates into distinct parts:

1

Role / Persona

Sets tone and domain framing ("You are a senior tax accountant...")

2

Task instruction

The single, unambiguous action to perform

3

Context

Background data the model needs but doesn't have (a document, a schema, prior turns)

4

Examples

Few-shot demonstrations, if the task needs them (§02)

5

Output format constraints

Exact shape of the expected answer — sets up §04's structured-generation topic

Common pitfall Fix
Vague verbs ("handle", "deal with", "look at") Name the exact action ("classify", "summarize in 3 bullet points", "extract the date field")
Instruction and examples disagree on format Make every example follow the exact format stated in the instruction, character-for-character
Negative instructions only ("don't be verbose") State the positive target instead ("respond in exactly 2 sentences") — models follow positive constraints more reliably
Burying the actual question under a long preamble Put the task/question close to the end of the prompt, right before generation starts
The decision rule for this whole section: start zero-shot. If accuracy is insufficient, add 2–4 well-chosen few-shot examples. If the task involves multiple reasoning steps, add chain-of-thought (few-shot or zero-shot). If a single CoT pass is still unreliable and the cost is acceptable, add self-consistency. Each step up this ladder costs more tokens — climb only as far as the accuracy bar requires.
Section 06

Key Takeaways & Exam Prep

✓

Zero-shot exploits instruction-tuning

Works when the task is common and the instruction is unambiguous.

✓

Few-shot is in-context learning

No weight updates; sensitive to example choice, order, and label balance.

✓

CoT trades tokens for computation

Spreading reasoning across generated tokens gives the model more forward passes per problem.

✓

Self-consistency votes on answers, not reasoning

K sampled paths, majority vote on the final extracted answer — an early form of test-time compute scaling.

✓

Climb the ladder only as needed

Zero-shot → few-shot → CoT → self-consistency, stopping as soon as accuracy is sufficient.

Common exam questions

Question Short answer
What's the difference between few-shot prompting and fine-tuning? Few-shot changes behavior temporarily via the prompt, no weight updates; fine-tuning (Module 1 §§03–06) permanently updates weights
Why does "let's think step by step" improve accuracy with zero examples? It pattern-matches the model into generating explicit intermediate reasoning tokens, which then serve as additional context/computation for the final answer
Why vote on the final answer instead of the full reasoning chain in self-consistency? Reasoning chains vary in wording even when correct; voting on the extracted final answer avoids needing to judge reasoning quality directly
What's the main risk of adding too many few-shot examples? Context dilution and diminishing/reversing returns — the actual query gets buried and irrelevant examples can bias output
