Advanced Reasoning

Beyond a single chain: search over reasoning paths (Tree/Graph-of-Thoughts), offloading computation to code (PAL/PoT), interleaving reasoning with tool use (ReAct), and self-correction (reflection, self-critique).

Section 01

Tree-of-Thoughts (ToT)

Chain-of-thought (Module 2 §01/§03) commits to a single reasoning path — one wrong step early on dooms the whole chain, and there's no way to look ahead or backtrack. Tree-of-Thoughts (Yao et al., 2023) reframes reasoning as a search problem: at each step, generate several candidate next-thoughts, evaluate them, keep the promising ones, and explore further — exactly like search algorithms explore a game tree.

FIG 1 — ToT explores multiple candidate thoughts at each step, uses a state evaluator to score/prune weak branches (B, A1, C1, C2), and expands only promising ones (A2) — like BFS/DFS over a game tree, with the LLM playing both "move generator" and "position evaluator."

The three components every ToT system needs

Component Role
Thought generator Given a partial solution, propose several plausible next steps (usually by sampling the LLM k times, or asking it to list k options)
State evaluator Score each candidate thought — "sure/likely/impossible" or a numeric value — often the same LLM, prompted to judge rather than generate
Search algorithm BFS (keep the best b candidates at each level) or DFS (follow the most promising path, backtrack on failure)
Exam favourite: "What does ToT add that chain-of-thought self-consistency (Module 2 §04) doesn't?" — self-consistency samples K complete, independent chains and votes at the end; it cannot backtrack mid-reasoning or share information across branches. ToT evaluates and prunes during generation, so a bad early step gets caught before wasting compute on the rest of that branch.
Section 02

Graph-of-Thoughts (GoT)

A tree only lets thoughts branch and get pruned — it never lets two separate branches merge. Graph-of-Thoughts (Besta et al., 2023) generalizes ToT's tree into an arbitrary graph: thoughts can be generated, refined, aggregated (combine two partial solutions into a better one), and even looped back on for further refinement.

Operation Tree-of-Thoughts Graph-of-Thoughts
Generate ✓ ✓
Evaluate / prune ✓ ✓
Backtrack ✓ (DFS) ✓
Aggregate (merge two branches) ✗ — branches are isolated ✓ — a node can have multiple parents
Refine (loop a thought on itself) ✗ ✓ — self-edges
When aggregation actually matters: tasks that decompose into independent sub-problems whose partial solutions need combining — e.g. sorting a long list by splitting into chunks, solving each chunk, then merging the sorted chunks. A tree structure has no operation for "merge branch 3 and branch 7's results" — GoT does, natively.
Cost reality: GoT's added flexibility comes from evaluating and merging more candidate thoughts, which means more LLM calls than ToT for the same problem. Reserve it for tasks that genuinely decompose-and-recombine; for tasks that are naturally a single decision sequence, ToT is cheaper for comparable quality.
Section 03

Program-of-Thoughts (PoT) & Program-Aided Language Models (PAL)

LLMs are unreliable at precise arithmetic and symbolic manipulation — not because they can't reason about the structure of a problem, but because token-by-token generation has no guaranteed calculator underneath it. PAL (Gao et al., 2022) and PoT (Chen et al., 2022) share one idea: have the LLM write the reasoning as executable code, then run that code in a real interpreter to get the final answer — instead of asking the LLM to compute the answer itself in natural language.

User: A store had 120 apples. They sold 35% on Monday and 20% of what remained on Tuesday. How many apples are left? # PAL/PoT-style output — code, not a text answer apples = 120 sold_monday = apples * 0.35 remaining_after_monday = apples - sold_monday sold_tuesday = remaining_after_monday * 0.20 remaining = remaining_after_monday - sold_tuesday print(remaining) → executed by a Python interpreter → 62.4
Why this beats plain CoT on math/logic tasks: chain-of-thought still asks the LLM to perform the arithmetic itself, in tokens — every multiplication is a chance for a token-level slip. PAL/PoT only asks the LLM to get the logic right (which operations, in what order); a real interpreter executes the arithmetic exactly, every time. The LLM's job shrinks to what it's actually reliable at: translating a word problem into correct code.
Chain-of-Thought PAL / PoT
Where the answer is computed By the LLM, in generated tokens By a real interpreter, executing generated code
Arithmetic reliability Can slip on multi-digit / multi-step math Exact, by construction
Requires Nothing extra A code execution environment (sandbox)
Best for Qualitative, linguistic, or fuzzy reasoning Math, counting, date arithmetic, symbolic manipulation
This is a special case of tool use. A code interpreter is just one tool an LLM can call. §04 (ReAct) generalizes "write code, run it, use the result" into "take any action — code, search, an API call — observe the result, and reason about what to do next."
Section 04

ReAct — Reasoning + Acting

ReAct (Yao et al., 2022) interleaves three things in a loop: a Thought (reasoning about what to do next), an Action (calling a tool — search, calculator, API, code executor), and an Observation (the tool's real-world result) — repeated until the model has enough information to answer.

FIG 2 — The ReAct loop: Thought decides what's needed, Action calls a real tool, Observation feeds the tool's actual result back in — grounding each subsequent Thought in reality rather than the model's possibly-outdated internal knowledge.
Thought: I need to find who directed the highest-grossing film of 2023. Action: search("highest grossing film 2023") Observation: "Barbie" grossed $1.44B, the highest of 2023. Thought: Now I need the director of Barbie. Action: search("Barbie 2023 director") Observation: Directed by Greta Gerwig. Thought: I have enough information to answer. Final Answer: Greta Gerwig.
Why interleaving beats "reason first, then act once": pure CoT reasoning can only use knowledge baked into the model's weights at training time — it hallucinates confidently when that knowledge is stale, missing, or wrong. ReAct grounds each reasoning step in a fresh Observation from the real world, and lets later Thoughts correct course based on what Actions actually returned — the loop, not a single lookup, is what makes it robust to a wrong first guess.
This is the mechanism behind agentic LLM systems. "Tool calling" and "function calling" (Module 2 §04's structured-generation counterpart) are the structured-output plumbing that makes the Action step reliable and parseable — ReAct is the reasoning pattern that decides when and what to call.
Section 05

Reflection-Based Reasoning

Every method so far generates an answer and stops. Reflection (notably Reflexion, Shinn et al., 2023) adds a loop on top of an attempt: after acting (e.g. running code that fails a test, or producing an answer that's checked and found wrong), the model generates a verbal self-reflection — a natural-language critique of what went wrong — and stores it in memory to inform the next attempt.

// Reflexion loop, one task episode attempt₁ = solve(task) result₁ = evaluate(attempt₁) // e.g. unit tests pass/fail if result₁ == FAIL: reflection = reflect("why did attempt₁ fail?", result₁) memory.append(reflection) // episodic memory — carried into the NEXT attempt attempt₂ = solve(task, memory) // same task, informed by its own past mistake
Ingredient Role
Actor Generates the attempt (the LLM doing the task)
Evaluator Scores the attempt — can be external and exact (unit tests, a verifier) or another LLM call
Self-reflection generator Given a failed attempt + its evaluation, writes a natural-language diagnosis, not just a score
Episodic memory Accumulates reflections across attempts on the same task — this is what lets performance improve without any weight update
Reflection vs. self-consistency: self-consistency (§04 of Module 2's Part 1) runs K independent attempts and votes — the attempts never learn from each other. Reflection runs attempts sequentially, and each one is explicitly informed by a natural-language critique of the previous failure. It trades parallelism for a much richer error signal.
Section 06

Self-Critique & Verification

A narrower, single-pass version of reflection: generate → critique → revise. The model produces a draft answer, then — in a separate pass, often with a different or more targeted prompt — is asked to find flaws in its own draft, then produces a revised answer incorporating the critique.

FIG 3 — Self-critique as a fixed three-pass pipeline: generate, critique with a dedicated "find flaws" prompt, revise incorporating the critique. Can be repeated for multiple rounds, or stopped once the critique pass finds nothing.
An honest limitation, worth knowing for exams: a model critiquing its own output shares the same blind spots that produced the error in the first place — if it didn't know something was wrong when generating, it may not recognize it as wrong when asked to critique either. Self-critique reliably catches surface issues (formatting, an obviously missed constraint) but is a weaker guarantee against errors rooted in genuine knowledge gaps. External verifiers (unit tests, a retrieval check, a separate specialized model) catch a different, often more reliable, class of error.
Verification source Catches Misses
Self-critique (same model) Formatting slips, obviously unmet instructions, internal inconsistency Errors from genuine knowledge gaps shared by generator and critic
External verifier (tests, rules, retrieval) Objective, checkable failure modes Anything outside what the verifier was built to check
Separate, stronger model as critic Some errors the weaker generator can't see in itself Cost of a second model call; still not a guarantee
Section 07

Choosing a Method

Method Adds Cost Best for
Chain-of-thought Explicit intermediate steps 1× call, longer output Any multi-step reasoning, as a baseline
Self-consistency K parallel votes K× calls Reducing variance on well-posed problems with a clear final answer
Tree-of-Thoughts Search + pruning over steps Many calls (generate + evaluate per node) Problems with real branching decisions and dead ends (puzzles, planning)
Graph-of-Thoughts Merge/aggregate across branches More than ToT Decompose-and-recombine problems
PAL / PoT Code execution instead of mental math 1× call + interpreter Arithmetic, counting, precise symbolic tasks
ReAct Real-world tool grounding Many calls (one per Thought/Action/Observation cycle) Tasks needing current/external information, multi-step tool use
Reflection Sequential learning from failure within one episode Multiple sequential attempts Tasks with a clear pass/fail signal (code, structured tasks)
Self-critique A dedicated find-flaws pass 2–3× calls Improving quality/completeness of open-ended output
These compose. A production agent commonly combines several: ReAct for tool use, wrapped in a reflection loop when a tool call fails, using PAL for any arithmetic sub-step, occasionally sampling several ToT branches at a genuinely ambiguous decision point. None of these are mutually exclusive.
Section 08

Key Takeaways & Exam Prep

✓

ToT turns reasoning into search

Generate, evaluate, and prune candidate thoughts instead of committing to one chain.

✓

GoT adds merge and refine

The one operation a tree structurally cannot do: combine two branches into one.

✓

PAL/PoT delegate arithmetic to code

The LLM's job shrinks to translating logic into code; a real interpreter computes.

✓

ReAct grounds reasoning in observations

Thought → Action → Observation, looped, corrects course using real-world feedback.

✓

Reflection learns within an episode

A verbal self-critique stored in memory informs the next attempt — no weight update.

✓

Self-critique shares the generator's blind spots

Reliable for surface errors; weaker on errors rooted in genuine knowledge gaps.

Common exam questions

Question Short answer
What can Graph-of-Thoughts do that Tree-of-Thoughts cannot? Aggregate/merge two separate branches into one combined thought — a tree only supports branching and pruning, not merging
Why does PAL improve accuracy on math word problems specifically? It moves the actual arithmetic out of token-by-token LLM generation and into a real code interpreter, which computes exactly
What does the "Observation" step in ReAct provide that pure chain-of-thought lacks? Real, current, external information from an actual tool call — grounding reasoning in reality rather than only the model's training-time knowledge
What's the key structural difference between reflection and self-consistency? Self-consistency runs independent parallel attempts and votes; reflection runs sequential attempts where each is informed by a critique of the previous failure
