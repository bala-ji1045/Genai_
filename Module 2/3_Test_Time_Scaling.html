Test-Time Scaling

A second axis for buying model capability — not more parameters or training data, but more compute spent thinking at inference time. Deliberate reasoning, majority voting, self-reflection, and the scaling curves that govern all three.

Section 01

What Is Test-Time Scaling?

Module 1 §07 covered train-time scaling: more parameters and more training tokens (Chinchilla) buy a better base model — paid for once, before deployment. Test-time scaling (also called inference-time compute scaling) is a second, independent lever: spend more compute per query, at answer time — more sampled reasoning paths, longer reasoning chains, more search — to buy higher accuracy on that one query, without changing the model's weights at all.

FIG 1 — The two axes are independent and stackable: a bigger/better-trained model AND more inference-time compute per query both improve accuracy, through completely different mechanisms and cost structures.
Why this became a big deal: OpenAI's o1/o3 and similar "reasoning models" made explicit what self-consistency (Module 2 Part 1 §04) had already hinted at — letting a model spend more tokens/samples "thinking" before answering can improve accuracy by more, for a given dollar, than simply training a bigger model. It reframes "how good is this model" into "how good is this model at a given inference budget" — the right comparison is a curve, not a single number.
Section 02

Deliberate Reasoning

Deliberate reasoning is simply allowing (or explicitly instructing) the model to generate a longer chain of intermediate reasoning before committing to a final answer — trading generation length for accuracy. "Reasoning models" are trained (via RL on verifiable reward, e.g. correct/incorrect on math and code problems) to learn when to keep reasoning rather than stopping early, often producing reasoning traces many times longer than a direct answer would need.

Approach How reasoning length is controlled
Prompted CoT (Module 2 Part 1 §03) Length follows naturally from "think step by step" — no explicit budget
Budget forcing Explicitly force the model to continue reasoning past its natural stopping point (e.g. append "Wait, let me double check" and continue generating) or cut it off at a token budget
RL-trained reasoning models Reasoning length is itself learned — the model is rewarded for correct final answers and implicitly learns how much deliberation different problem difficulties need
The trade-off is explicit, not hidden: longer reasoning traces cost more tokens (latency + money) in direct proportion to their length. Deliberate reasoning is a dial, not a free upgrade — the question test-time scaling as a field is really asking is "for a fixed accuracy target, what's the cheapest way to spend inference compute to reach it?"
Section 03

Majority Voting, at Scale

Self-consistency (Module 2 Part 1 §04) is the simplest test-time scaling method: sample K independent reasoning paths, vote on the final answer. This section asks the natural follow-up — how does accuracy actually behave as K grows, and where are the practical limits?

FIG 2 — Majority voting accuracy climbs quickly at low K, then flattens toward a ceiling. That ceiling is set by whether the model's correct answer distribution actually outweighs any single wrong-but-plausible answer — if the model is systematically wrong (not just noisy), no amount of voting fixes it.
Exam favourite: "Does majority voting always improve accuracy as K increases?" — No. It helps when errors are diverse and unbiased (each wrong path tends to land on a different wrong answer, so the correct answer still wins the plurality). It does not help against a systematic error — if the model consistently reasons its way to the same wrong answer, voting more just gets a more confident wrong answer.
Section 04

Self-Reflection as Compute Allocation

Module 2 Part 2 §05 introduced reflection as a way to improve correctness through iterative self-critique. Viewed through the test-time scaling lens, reflection is really a different way of spending the same inference budget: instead of K parallel independent samples (majority voting), spend those tokens on a smaller number of sequential, informed attempts.

Majority voting (parallel) Reflection (sequential)
Attempts K independent, simultaneous Fewer, each informed by the previous one's failure
Information sharing between attempts None Explicit — a natural-language critique carried forward
Best when Errors are diverse/random across samples Errors are diagnosable — a critique can identify what specifically went wrong
Failure mode Systematic bias survives voting (§03) Reflection can loop without converging if the critique itself is flawed
They're not mutually exclusive. A practical system can combine both: sample several independent attempts (parallel), and within each, allow a couple of reflection rounds (sequential) — spending a fixed total inference budget along whichever axis the task responds to better.
Section 05

Inference-Time Compute Scaling Laws

Just as Module 1 §07 showed loss decreasing predictably with training compute (Chinchilla), research on test-time scaling (notably Snell et al., 2024, and OpenAI's o1 report) shows a similar pattern for inference compute: plotted on a log scale, accuracy tends to improve roughly linearly with the log of inference-time compute spent per query — up to a point.

// Schematic relationship (not a universal law — task- and model-dependent) accuracy ≈ a · log(inference_compute) + b // up to a ceiling // "Inference compute" here bundles several knobs that all cost tokens: // - K, the number of sampled reasoning paths (§03) // - reasoning chain length per sample (§02, "deliberate reasoning") // - search breadth/depth if using Tree-of-Thoughts (Module 2 Part 2 §01)

A key finding: small model + test-time compute can beat a bigger model

Snell et al. (2024) showed that, on math benchmarks, a smaller model given a larger inference-time compute budget (more sampling/search) can outperform a substantially larger model given a smaller inference budget, for the same total compute. This is the practical reason test-time scaling matters as a design decision, not just a research curiosity: it changes where the compute budget is best spent.

The caveat that makes this a genuine trade-off, not a free lunch: train-time compute is paid once and amortized across every future query forever; test-time compute is paid again, every single query. A cheap-to-train, expensive-to-run model can be the wrong choice for a high-volume production system even if it's the right choice for a low-volume, accuracy-critical one (e.g. a hard one-off math problem vs. a customer-support chatbot serving millions of requests).
Scenario Favors
Low query volume, high accuracy stakes (research, hard one-off problems) Heavier test-time compute — sample more, reason longer
High query volume, cost-sensitive (consumer chat, high-traffic APIs) Heavier train-time investment in a better base model, lighter test-time budget per query
Unknown query difficulty ahead of time Adaptive compute — spend more only when an easy first pass indicates the problem is actually hard
Section 06

Key Takeaways & Exam Prep

✓

A second, independent axis

Test-time compute buys accuracy on one query; train-time compute buys a better model for every future query.

✓

Deliberate reasoning is a length dial

Longer reasoning traces cost proportionally more tokens — an explicit, tunable trade-off.

✓

Majority voting has a ceiling

Helps against diverse/random errors; does nothing against systematic bias.

✓

Reflection reallocates the same budget sequentially

Fewer, informed attempts instead of many independent ones.

✓

Small model + big inference budget can beat big model + small budget

For fixed total compute — but train-time cost amortizes, test-time cost doesn't.

Common exam questions

Question Short answer
What's the fundamental difference between train-time and test-time scaling? Train-time compute is spent once, before deployment, improving the model for all future queries; test-time compute is spent per query, at inference, improving the answer to that one query
Why doesn't majority voting always improve with more samples? It corrects for diverse/random errors across samples, but not for a systematic bias the model consistently reasons into — voting more just increases confidence in the same wrong answer
Why might a smaller model with a larger test-time budget beat a larger model with a smaller one? For a fixed total compute budget, spending it on more inference-time reasoning/search can yield higher accuracy than spending the same compute on training a bigger model — shown empirically on math benchmarks (Snell et al., 2024)
When should you prefer investing in train-time over test-time compute? High query volume, cost-sensitive deployments — train-time cost amortizes across all future queries, while test-time cost repeats every single query
