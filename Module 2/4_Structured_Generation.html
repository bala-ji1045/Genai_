Section 01

Why Structure?

An LLM is, at its core, a next-token sampler over free-form text (Module 1 §01). But almost every real system built on top of one needs the output to be parseable — a downstream function that expects a specific field, a database row, an API call with named arguments. "Structured generation" is the umbrella term for techniques that make an LLM's raw text output reliably conform to a schema.

The naive approach fails silently. Just asking nicely — "please respond in JSON" — usually works most of the time, and that's exactly the problem: "most of the time" means a production system needs a parser that can crash, retry logic, or silent data corruption on the failures. Structured generation techniques exist to convert "usually correct" into "guaranteed correct by construction."
Section 02

JSON Outputs

There are two fundamentally different ways to get JSON out of an LLM, and they give very different guarantees.

Approach Mechanism Guarantee
Prompted JSON Ask for JSON in the instruction, maybe show an example None — the model can still emit malformed JSON, extra prose, or a wrong schema
Constrained decoding At each generation step, mask out any token that would make the output invalid against a grammar/schema — only valid next-tokens are ever sampled Syntactically valid JSON matching the schema, by construction
FIG 1 — Constrained decoding intersects the model's normal probability distribution with the set of tokens a formal grammar (the JSON schema) allows at this position — the same −∞-masking mechanism as causal masking (Module 1 §05), applied to schema validity instead of future position.
What this costs you: constrained decoding guarantees valid syntax, not valid content — a schema can force "age" to be a number, but can't force it to be the correct age. It also requires infrastructure support (a grammar-aware sampler, e.g. via outlines, guidance, or a provider's native "JSON mode"/"structured outputs" feature) — not every deployment has this available, especially for closed models accessed only via a plain text API.
Section 03

Tool Calling & Function Calling

"Function calling" is JSON-structured output applied to a specific purpose: instead of (or alongside) a text answer, the model emits a structured request to invoke a named function with specific arguments — which your application code actually executes, then feeds the result back in (this is the plumbing underneath ReAct's Action step, Module 2 Part 2 §04).

FIG 2 — Function calling as a full round trip: the model never executes anything itself — it only ever emits a structured request; your application code is what actually runs the function and returns a real result.
# The tool "schema" the model is given — a JSON Schema describing the function signature tools = [{ "name": "get_weather", "description": "Get current weather for a city", "parameters": { "type": "object", "properties": { "city": { "type": "string"}}, "required": [ "city"] } }] # The model returns a tool_call, not free text, when it decides to use this tool — # your code is responsible for matching the name, executing it, and returning the result.
"Tool calling" and "function calling" are the same mechanism, just named differently by convention — "function calling" for calling a specific named function (as above), "tool calling" as the more general umbrella that also covers things like a code interpreter or a retrieval system exposed the same way. Neither name implies a different underlying protocol.
Section 04

LangChain — Composing Prompts, Tools, and Models

LangChain is a framework for wiring together the pieces a real LLM application needs: prompts, models, tools, memory, and multi-step control flow — as composable objects instead of hand-written glue code.

Concept What it is
Chain A fixed sequence of steps (prompt → model → parser → next prompt → ...) — the pipeline is defined ahead of time
Agent A loop where the model itself decides, at each step, which tool to call next (this is exactly the ReAct pattern from Module 2 Part 2 §04, implemented as reusable infrastructure)
Tool Any callable — a search API, a calculator, a database query — wrapped with a description the model can read and decide to invoke
Memory Carries conversation history or intermediate state across chain/agent steps
from langchain.agents import initialize_agent, Tool from langchain_openai import ChatOpenAI tools = [Tool(name= "search", func=web_search, description= "search the web")] llm = ChatOpenAI(model= "gpt-4o") agent = initialize_agent(tools, llm, agent= "react") agent.run( "Who directed the highest-grossing film of 2023?") # Internally runs exactly the Thought/Action/Observation loop from Module 2 Part 2 §04
What LangChain is really buying you: not new capability — everything it does is expressible as raw prompts and API calls — but standardized, reusable plumbing for patterns (agents, memory, retrieval, tool schemas) that would otherwise be reimplemented, slightly differently and slightly buggily, in every project.
Section 05

DSPy — Prompts as Optimizable Programs

Hand-writing and tweaking prompt strings ("prompt engineering" as trial-and-error string editing) doesn't scale well, and a prompt tuned for one base model often breaks when swapped for another. DSPy (Khattab et al., 2023) reframes the problem: instead of writing prompt strings, you declare what transformation you want (a signature — input fields → output fields), and DSPy compiles that declaration into an actual prompt, which can then be automatically optimized.

import dspy # A signature: declare the transformation, not the prompt wording class AnswerQuestion(dspy.Signature): """Answer the question using the given context.""" context = dspy.InputField() question = dspy.InputField() answer = dspy.OutputField() # A module: how the signature gets EXECUTED (here, with chain-of-thought) qa = dspy.ChainOfThought(AnswerQuestion) result = qa(context= "Paris is the capital of France.", question= "What is the capital of France?") print(result.answer) # DSPy generated and ran the actual prompt behind the scenes
DSPy concept Role
Signature Declares input/output fields and a task description — the "what," not the "how"
Module A strategy for executing a signature — Predict (direct), ChainOfThought (adds reasoning, Module 2 Part 1 §03), ReAct (tool use, Module 2 Part 2 §04) — swap strategies without rewriting the task
Program A composition of modules — multi-step pipelines built like ordinary code, not string concatenation
Metric A function scoring whether a program's output on a training example was good — the objective §06's optimizer maximizes
The reframe, in one sentence: classic prompt engineering treats the prompt string as the artifact you hand-tune; DSPy treats the prompt string as a compiled output — you write the program (signatures + modules) and a metric, and let an optimizer generate/select the actual wording.
Section 06

Prompt Optimization with DSPy

DSPy's optimizers (called teleprompters) automatically improve a program's prompts against a training set and a metric — without you hand-editing wording. The most common one, BootstrapFewShot, automates exactly the example-selection problem from Module 2 Part 1 §02.

FIG 3 — BootstrapFewShot: run the un-optimized program on training examples, keep only the self-generated reasoning traces whose final answer scores well against the metric, and use those as the few-shot examples in the compiled prompt — automating what Module 2 Part 1 §02 does by hand.
from dspy.teleprompt import BootstrapFewShot def exact_match_metric(example, prediction, trace= None): return example.answer.lower() == prediction.answer.lower() optimizer = BootstrapFewShot(metric=exact_match_metric) compiled_qa = optimizer.compile(qa, trainset=train_examples) # compiled_qa now has automatically-selected few-shot examples baked in — # no prompt string was ever hand-written or hand-tuned
Teleprompter Strategy
BootstrapFewShot Self-generate and filter few-shot examples by the metric (above)
BootstrapFewShotWithRandomSearch Try multiple candidate example sets, keep the best on a validation split
MIPRO Jointly optimizes both the instruction wording and the few-shot examples
Why this matters for the "prompt optimization" lab: manually iterating on prompt wording is slow, subjective, and doesn't transfer between models. Declaring a signature + metric + training set turns prompt quality into something you can measure and automatically search over — the same generate → evaluate → keep-the-best loop that shows up throughout Module 2 (self-consistency's voting, ToT's pruning, reflection's critique), applied here to the prompt itself rather than to an individual answer.

Key Takeaways & Exam Prep

✓

"Please respond in JSON" is a request; constrained decoding is a guarantee.

✓

✓

No new capability — reusable infrastructure for patterns like ReAct.

Common exam questions

Question Short answer
What's the difference between prompted JSON and constrained decoding? Prompted JSON asks the model to produce valid JSON with no guarantee; constrained decoding masks out any next-token that would violate the schema, guaranteeing syntactic validity by construction
Does the model ever actually execute a tool/function itself? No — it only emits a structured request (name + arguments); the calling application executes the real function and returns the result
What is a DSPy "signature"? A declaration of a task's input and output fields plus a description — what transformation is wanted, independent of any specific prompt wording
How does BootstrapFewShot choose its few-shot examples? It runs the program on training examples, keeps the self-generated reasoning traces whose final answer scores well against a metric, and uses those as the compiled prompt's examples
