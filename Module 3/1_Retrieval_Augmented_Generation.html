Section 01

Introduction to Embeddings, Revisited for Retrieval

Module 1 §03 introduced embeddings as a token-level lookup table inside an LLM. RAG uses a related but distinct idea: a sentence/document embedding — one dense vector representing the meaning of an entire passage, produced by a model specifically trained so that semantically similar texts land close together in vector space, regardless of shared vocabulary.

Token embedding (Module 1 §03) Sentence/document embedding (this module)
Granularity One vector per token One vector per chunk/sentence/document
Produced by The LLM's own embedding layer, as part of the model A dedicated embedding model (e.g. Sentence-Transformers), used standalone
Trained for Whatever helps next-token prediction Similarity: "these two texts mean the same thing" → close vectors
Used for Feeding a Transformer's attention layers Nearest-neighbor search over a corpus (§02)

Cosine similarity — the standard way to compare two embeddings

// Cosine similarity between two vectors — measures ANGLE, not magnitude cos_sim(a, b) = (a · b) / (‖a‖ × ‖b‖) // Range: -1 (opposite meaning) to 1 (identical meaning); 0 = unrelated // Why angle, not raw distance? Two embeddings can point the same direction // (same meaning) but have different lengths (e.g. one text is longer) — // cosine similarity ignores magnitude entirely, comparing only direction.
Why a dedicated embedding model, not the LLM's own embeddings? An LLM's internal token embeddings are optimized for next-token prediction, not for "which two documents mean the same thing" — using them directly for retrieval works poorly. Sentence-embedding models (e.g. sentence-transformers/all-MiniLM-L6-v2) are trained with a contrastive objective specifically to pull similar-meaning texts together and push dissimilar ones apart in vector space.
Section 02

Semantic Search

Semantic search retrieves documents by meaning rather than exact keyword overlap: embed the query, embed every candidate document, and return the documents whose embeddings are closest (by cosine similarity) to the query's embedding.

FIG 1 — Keyword search matches literal terms; semantic search matches meaning. Neither is strictly better — §06 (Hybrid Retrieval) combines both because each catches what the other misses.
Exam favourite: "Why can semantic search sometimes perform worse than keyword search?" — dense embeddings compress meaning into a fixed-size vector and can blur exact tokens that matter precisely for retrieval — product SKUs, error codes, proper nouns, numbers. This is precisely why hybrid retrieval (§06) exists.

Worked example: cosine similarity by hand

Real embeddings have hundreds of dimensions, but the mechanics are identical in two: represent each text as a unit-length vector at some angle, and cosine similarity reduces to cos(angle between them) — the same dot-product formula above, just easy to see.

// Toy 2D embeddings, illustrative only — real ones are 384-dim (e.g. all-MiniLM-L6-v2) query "how to reduce fever in kids" → angle 30° → ( 0.866, 0.500) doc A "fever reduction methods for children" → angle 25° → ( 0.906, 0.423) doc B "bringing down a child's temperature" → angle 40° → ( 0.766, 0.643) doc C "quarterly financial report" → angle 120° → (-0.500, 0.866) // For unit vectors, cos_sim(a, b) = cos(angle_a − angle_b) — no division needed cos_sim(query, A) = cos(30° − 25°) = cos(5°) = 0.996 cos_sim(query, B) = cos(30° − 40°) = cos(−10°) = 0.985 cos_sim(query, C) = cos(30° − 120°) = cos(−90°) = 0.000 // Ranking: A (0.996) > B (0.985) ≫ C (0.000)
Doc B still beats doc C despite sharing zero words with the query ("bringing down a child's temperature" vs. "reduce fever in kids"). This is FIG 1 made numeric: the embedding model placed both phrasings of the same underlying meaning at nearly the same angle, so cosine similarity ranks them almost identically — while the genuinely unrelated document lands at a right angle (90°) and scores exactly zero, by definition of what cosine similarity measures.
Section 03

Vector Databases — FAISS

Comparing a query embedding against every document embedding one-by-one (brute force) is O(n) per query — fine for thousands of documents, too slow for millions. FAISS (Facebook AI Similarity Search) is a library of approximate nearest-neighbor (ANN) index structures that trade a small amount of recall for large speedups.

Index type How it works Trade-off
Flat (brute force) Compares the query against every vector, exactly 100% recall, but O(n) — fine up to ~100k vectors
IVF (Inverted File) Clusters vectors into buckets (via k-means); only searches the nearest bucket(s) Much faster; recall depends on how many buckets are probed
HNSW (Hierarchical Navigable Small World) Builds a multi-layer graph of vectors; search "walks" the graph toward the query Very fast, high recall; more memory, slower to build
PQ (Product Quantization) Compresses each vector into a short code; distances computed approximately on the codes Massive memory savings; some recall loss — often combined with IVF (IVF-PQ)
// Minimal FAISS usage — the mechanics behind §s2 & the lab notebook import faiss index = faiss.IndexFlatIP(embedding_dim) // IP = inner product (~cosine, if vectors are normalized) index.add(document_embeddings) // shape: [n_docs, embedding_dim] D, I = index.search(query_embedding, k=5) // D = similarity scores, I = indices of top-5 docs
Why "vector database" rather than just "an index in memory"? A vector database (FAISS itself is a library, not a full database — Pinecone, Weaviate, Qdrant, pgvector are full databases built on similar ANN principles) adds what a raw index lacks: persistence, metadata filtering (search only documents where category="finance"), incremental updates, and horizontal scaling. FAISS is the right choice for local/embedded use or as the ANN engine underneath a larger system; a managed vector DB is the right choice when you need those extra operational features.

Worked example: all four index types, same corpus, same query

Real, computed results — same 16-document corpus and query as the lab notebook ( "What is the rate limit for endpoint /v2/limits?"), each index type actually built and searched with FAISS.

1. Flat (exact, brute-force)

index = faiss.IndexFlatIP(384); index.add(vecs) // vecs = 16 x 384 D, I = index.search(query_vec, k=3) // Ground truth — compares the query against all 16 vectors, exactly: top-3 = doc 15 (sim 0.634), doc 7 (sim 0.270), doc 13 (sim 0.251)

2. IVF (Inverted File), nlist = 4 clusters

The 16 vectors get k-means-clustered into 4 buckets; a search only compares the query against vectors in the nprobe nearest bucket(s) instead of all 16:

// Real cluster assignment for all 16 docs (cluster id per doc, in order 0-15): [3, 1, 3, 0, 3, 1, 3, 0, 3, 1, 1, 0, 2, 3, 3, 3] // The query embeds into cluster 3 — an 8-document bucket nprobe=1 (search only cluster 3): top-3 = doc 15, doc 13, doc 4 ← WRONG, misses doc 7 nprobe=2 (search 2 nearest clusters): top-3 = doc 15, doc 13, doc 4 ← still wrong nprobe=4 (search ALL clusters, = nlist): top-3 = doc 15, doc 7, doc 13 ← matches Flat exactly
Doc 7 ("Support ticket priority levels...") lives in a different cluster than the query — cluster 1, not cluster 3 — so with nprobe=1 or nprobe=2, IVF never even looks at it, and doc 4 (a worse match) takes its place in the results. This is a real recall failure caused entirely by clustering, on a corpus of just 16 documents — the same failure mode, at any scale, is why nprobe is the parameter you tune to trade search speed against how often this happens.

3. PQ (Product Quantization), 8 subquantizers × 2 bits

Each 384-dim, 1536-byte (float32) vector gets compressed into a short code — split into 8 sub-vectors of 48 dimensions each, and each sub-vector replaced by the id of its nearest of 4 trained centroids:

// Real compression ratio and reconstruction error, computed on this corpus: code size = 8 subquantizers × 2 bits = 16 bits = 2 bytes per vector compression = 1536 bytes → 2 bytes = 768x smaller reconstruction L2 error (doc 0, decompressed vs. original) = 0.747 // Search on the COMPRESSED codes: top-3 = doc 15, doc 7, doc 4 ← misses doc 13 this time (vs. Flat's doc 15, 7, 13)
768x smaller, and it still gets the #1 result right — but the compression is lossy enough that doc 13 (a legitimate 3rd-place match) gets replaced by doc 4. This is the direct trade PQ makes: at billion-vector scale, holding every vector as raw float32 simply doesn't fit in memory, so a few percentage points of recall are traded for a dataset that fits at all.

4. HNSW (graph-based)

Builds a multi-layer graph where each vector links to its approximate nearest neighbors; a search starts at an entry point in the top (sparse) layer and greedily walks toward the query, descending layers as it converges:

index = faiss.IndexHNSWFlat(384, M=16, metric=faiss.METRIC_INNER_PRODUCT) index.hnsw.efConstruction = 40; index.add(vecs) index.hnsw.efSearch = 8 top-3 = doc 15 (0.634), doc 7 (0.270), doc 13 (0.251) ← matches Flat EXACTLY
A real, easy-to-hit FAISS gotcha: faiss.IndexHNSWFlat(d, M) defaults to L2 distance, not inner product/cosine — passing metric=faiss.METRIC_INNER_PRODUCT explicitly (as above) is required to match the metric used everywhere else in this pipeline. Build it with the default constructor and you'll get silently different (though often still plausible-looking) rankings, with no error raised anywhere.
Section 04

The RAG Pipeline, End to End

RAG grounds an LLM's answer in retrieved documents instead of relying purely on what's baked into its weights — the same core idea as ReAct's grounding (Module 2 Part 2 §04), specialized to one specific tool: a retriever over your own document corpus.

FIG 2 — Two distinct phases: index-time runs once (or periodically — see §10) over the whole corpus; query-time runs on every single user question. Confusing the two is the single most common RAG design mistake.
The core mental model for the whole module: RAG doesn't make the LLM smarter — it changes what's in the LLM's context window. Every section from here on (chunking, hybrid retrieval, re-ranking) is really answering one question: how do we make sure the right information ends up in that context window, and the wrong information doesn't?
Section 05

Chunking Strategies

Documents are too long to embed and retrieve as a single unit — a 50-page PDF embedded as one vector loses almost all specific detail. Chunking splits documents into retrieval-sized pieces before embedding.

Strategy How it splits Trade-off
Fixed-size (character) Every N characters, regardless of content Simplest possible; frequently cuts mid-word or mid-sentence — see the worked example below
Fixed-size (token) Every N tokens, counted with the target embedding/LLM's own tokenizer Aligns chunk size with the model's actual context budget rather than raw characters; still content-blind
Recursive character splitting Tries paragraph breaks first, falls back to sentences, then words, then raw characters, until chunks fit the size budget Respects natural boundaries far better than fixed-size; still somewhat arbitrary at the chosen size
Sentence-based splitting Splits strictly on sentence boundaries (via a sentence tokenizer), then packs whole sentences into each chunk up to the size budget Never breaks a sentence in half; resulting chunk sizes vary more than fixed-size methods
Structure-aware splitting Splits on the document's own structural markers — Markdown headers, HTML tags, code fences, table rows Keeps a genuine logical unit (a subsection, a function, a list) intact; needs a parser tailored to each document format
Sliding window Fixed-size chunks advanced by a stride smaller than the chunk size, so consecutive chunks overlap heavily Guarantees boundary content is never isolated in just one chunk; multiplies index size, since most text gets embedded more than once
Semantic chunking Embeds individual sentences, then splits where the similarity between consecutive sentences drops sharply — i.e. where the topic actually changes Chunks align with real conceptual units, not an arbitrary size; needs an extra embedding pass just to build the index
Parent-document (hierarchical) Small child chunks are embedded and searched for precision, but retrieval returns each match's larger parent chunk or section for generation Combines precise matching with complete surrounding context; requires maintaining a child→parent mapping
Two further techniques worth knowing by name: agentic chunking has an LLM read the document and propose chunk boundaries directly, based on where it judges ideas to actually begin and end — often the most semantically coherent result, at the cost of an LLM call (and non-determinism) per document. Late chunking inverts the usual order: embed the entire document at once with a long-context embedding model, then pool the resulting token embeddings into chunks afterward — so each chunk's vector still carries context from the whole document, rather than only from its own short span.

Overlap — why chunks usually share a border

FIG 3 — Without overlap, a sentence spanning the exact chunk boundary can end up split across two chunks, with neither chunk containing the complete idea. A small overlap (10-20% of chunk size) ensures boundary content is fully present in at least one chunk.
Chunk size Retrieval precision Context completeness
Small (e.g. 128 tokens) Higher — less irrelevant content per chunk Lower — may miss surrounding context needed to interpret the chunk
Large (e.g. 1024 tokens) Lower — more irrelevant content dilutes the match Higher — more surrounding context included
There's no universally correct chunk size. It's a genuine hyperparameter to tune against your own evaluation set (§08) — dense, fact-heavy documents (legal text, API docs) often favor smaller chunks; narrative or explanatory content often favors larger ones.

4. Sentence-based splitting

One chunk per sentence, with no fixed size budget at all:

Which is "correct" so far? All three non-fixed-size methods above happen to preserve every sentence intact for this text — a property of where the chosen sizes land relative to sentence length here, not a guarantee. Shrink the character budget to 60 and even the recursive splitter starts breaking sentences, just far less often than fixed-size does. Sentence-based splitting is the only one that structurally cannot sever a sentence, at the cost of giving up any fixed chunk-size guarantee.

5. Structure-aware splitting

The same content, but authored with Markdown headers (a very common real case — knowledge-base articles, READMEs, wikis). A structure-aware splitter cuts on the headers themselves, keeping each section whole regardless of character count:

// Source Markdown ## Returns Acme Corp's return policy allows customers to return any unopened product within 30 days of purchase for a full refund. Opened electronics may be returned within 14 days if all original accessories and packaging are included. ## Refunds Refunds are issued to the original payment method and typically appear within 5 to 7 business days. ## Final Sale Items Items marked 'final sale' cannot be returned or exchanged under any circumstances. // Split on "## " boundaries -> 3 chunks, each a complete section: Chunk 1 "## Returns\n" + the returns paragraph Chunk 2 "## Refunds\n" + the refunds sentence Chunk 3 "## Final Sale Items\n" + the final-sale sentence
Notice chunk 2 is only one sentence — far shorter than a fixed 120-character budget would produce, and chunk 1 spans two sentences. A structure-aware splitter doesn't care: it trusts that whoever wrote the document already marked out the logical units with headers, and respects that boundary over any size target.

6. Sliding window, chunk_size = 150 chars, stride = 100 chars

Fixed windows that advance by less than their own size, so every chunk overlaps the next by 50 characters:

Chunk 1 (chars 0-150): "Acme Corp's return policy allows customers to return any unopened product within 30 days of purchase for a full refund. Refunds are issued to th" Chunk 3 (chars 200-350): " d packaging are included. Refunds are issued to the original payment method and typically appear within 5 to 7 business days. Items marked 'final sale" Chunk 4 (chars 300-408): " hin 5 to 7 business days. Items marked 'final sale' cannot be returned or exchanged under any circumstances." // Every 50-character span appears in TWO chunks — more redundant than the 20-char // overlap in method 3, but it guarantees no boundary content is ever isolated, // at the cost of embedding roughly 1.5x more text than the source contains.

7. Semantic chunking

Semantic chunking needs more than one topic to show its actual value — so extend the example with two unrelated sentences appended, and embed each sentence individually with all-MiniLM-L6-v2 to measure how similar each one is to the sentence right after it:

// 5 real sentences, real consecutive-sentence cosine similarities S1 "The company's return policy allows returns within 30 days..." S2 "Refunds are processed within 5-7 business days after..." S3 "Items marked 'final sale' cannot be returned or exchanged..." S4 "The API rate limit is 1000 requests per minute per API key..." S5 "Support ticket priority levels are P1 (critical, 1hr)..." sim(S1, S2) = 0.695 // both about returns/refunds — stay together sim(S2, S3) = 0.370 // still policy-related, but a smaller dip sim(S3, S4) = 0.053 // the topic changes entirely — the real split point sim(S4, S5) = 0.264 // both about the support/API topic — stay together // Split at the single largest similarity DROP (0.053, far below the others): Chunk A = [S1, S2, S3] (return/refund policy) Chunk B = [S4, S5] (API/support reference)
This is the one method that used the actual meaning of the text, not its position or size. A fixed-size or recursive splitter has no way to know that S3 and S4 are unrelated — it would just as happily place the cut between S2 and S3 (also a plausible-looking sentence boundary) as between S3 and S4. Semantic chunking finds the real seam because it's the only method that measures the content on both sides of every candidate cut.

8. Parent-document (hierarchical) chunking

Index each sentence of the original paragraph individually as a small, precise child chunk — but map every child back to the full paragraph as its parent, and return the parent (not just the matched sentence) at generation time:

Child chunk (searched) Parent returned (used for generation)
"Acme Corp's return policy allows customers to return any unopened product within 30 days of purchase for a full refund." The full 408-character paragraph (all 4 sentences)
"Opened electronics may be returned within 14 days if all original accessories and packaging are included."
"Refunds are issued to the original payment method and typically appear within 5 to 7 business days."
"Items marked 'final sale' cannot be returned or exchanged under any circumstances."
Why this matters for a question like "how long do refunds take?" The child sentence "Refunds are issued... within 5 to 7 business days" is the single best-matching chunk — precise retrieval. But answered from that sentence alone, the model has no way to also mention the final-sale exception or the 14-day electronics window. Returning the parent paragraph gives the LLM the complete surrounding context that made the precise match possible in the first place, without diluting the search index with oversized chunks.
Section 06

Retrieval — Hybrid Retrieval & BM25

BM25 is a classic sparse, keyword-based ranking function (a statistical refinement of TF-IDF) — it scores documents by term frequency, downweighted for common words and document length. Unlike dense embeddings, it matches exact tokens.

// BM25 score, conceptually (full formula has 2 tuning constants k1, b) score(D, Q) = Σ_term IDF(term) × [ TF(term, D) saturating with frequency, normalized by doc length ] // Key properties: // - rare terms across the corpus score higher (IDF) // - repeating a term helps, but with DIMINISHING returns (saturation) // - longer documents are penalized relative to their length

Hybrid retrieval: dense + sparse, combined

Dense (embeddings, §01-§03)
  • Catches paraphrase, synonyms, meaning
  • Weak on exact identifiers, rare tokens, numbers
Sparse (BM25)
  • Exact keyword/identifier matching, cheap, no training needed
  • Blind to paraphrase — zero overlap means zero score
// Reciprocal Rank Fusion (RRF) — a common way to combine two ranked lists RRF_score(doc) = Σ_retriever 1 / (k + rank_in_that_retriever(doc)) // k ~ 60, a smoothing constant // A document ranked #1 by BOTH dense and sparse retrieval scores much higher // than one ranked #1 by only one — this is what "hybrid" actually computes.
Why hybrid, not "pick the better one": §02's FIG 1 showed dense search missing nothing lexically similar and sparse search missing paraphrase — the failure modes are close to disjoint. Running both and fusing the rankings (RRF above, or a learned combination) recovers documents either retriever alone would have missed.

These are the actual numbers 1_RAG_Pipeline_Lab.ipynb produces over its 16-document corpus (its Section 1) — reproducible by re-running the notebook's Sections 3-5 yourself.

Why is BM25's score for doc 15 so much larger than everything else? The tokens limit and limits each appear in exactly one document out of sixteen — an extremely rare term earns an extremely high IDF weight in BM25's formula (above), so any document containing it dominates the ranking. Dense retrieval finds the same top document, but by meaning rather than a lucky token match — its 2nd/3rd-place picks ([7], [13]) are topically related "support/spec" documents rather than lexical near-misses.

Fusing both lists with RRF ( k_const = 60):

// doc 15: rank 1 in BOTH lists RRF(15) = 1/(60+1) + 1/(60+1) = 1/61 + 1/61 = 0.0328 // doc 13: rank 3 in BOTH lists RRF(13) = 1/(60+3) + 1/(60+3) = 1/63 + 1/63 = 0.0317 // doc 7: rank 2 in dense ONLY — never appears in BM25's top-5 at all RRF(7) = 1/(60+2) + 0 = 1/62 = 0.0161 // Final fused top-3: [15] 0.0328 > [13] 0.0317 > [7] 0.0161 // — exactly what the notebook's hybrid_retrieve() prints for this query.

Now the opposite case — a paraphrase query: "How much time off do new hires get each year?", which shares almost no words with the document that actually answers it.

Rank Dense retrieval (FAISS) Sparse retrieval (BM25)
1 [1] "Employees are entitled to 15 days of paid annual leave..." [12] score = 2.62
2 [9] "New employees complete a 90-day probationary period..." [9] score = 2.53
3 [12] "Remote employees receive a one-time $500 stipend..." [1] score = 2.30
4 [14] "Price matching is honored within 14 days..." [15] score = 0.00
5 [0] "The company's return policy allows returns..." [14] score = 0.00
BM25 isn't wrong here, it's just working from the wrong signal. "new", "employees", and "days" are literal words the query and several documents share, so BM25 ranks [12] and [9] highly — by coincidence of vocabulary, not because it understood "time off" means "annual leave." Dense retrieval ranks [1] (the actual leave policy) first precisely because it never relied on shared words in the first place.
// doc 1: rank 1 dense, rank 3 BM25 RRF(1) = 1/61 + 1/63 = 0.01639 + 0.01587 = 0.0323 // doc 12: rank 3 dense, rank 1 BM25 — the same two rank VALUES as doc 1, just swapped RRF(12) = 1/63 + 1/61 = 0.01587 + 0.01639 = 0.0323 // doc 9: rank 2 in BOTH lists RRF(9) = 1/62 + 1/62 = 0.01613 + 0.01613 = 0.0323 // All three round to the same fused score — this is exactly what the notebook // prints: three results, all rrf_score=0.0323
RRF rewards the SET of ranks a document collects, not which retriever produced them. Doc 1 and doc 12 land on exactly the same fused score despite disagreeing about which one deserves rank 1 — because RRF sums 1/(k+rank) across retrievers, and {1,3} sums to the same total as {3,1}. This is why re-ranking (§07) still matters after fusion: RRF settles disagreements about ordering, but doesn't itself judge relevance the way a cross-encoder does.
Section 07

Re-ranking

Retrieval (dense, sparse, or hybrid) is optimized to be fast across potentially millions of documents — it uses cheap similarity computations. A re-ranker is a second, slower, more accurate stage: take the top-k candidates retrieval already narrowed things down to, and score each one properly against the query.

FIG 4 — Retrieval's bi-encoder embeds query and document separately (allowing documents to be pre-embedded once); a cross-encoder re-ranker embeds them together, letting query and document tokens attend to each other directly — more accurate, but only affordable on a small top-k shortlist, not the whole corpus.
Exam favourite: "Why not just use a cross-encoder for retrieval directly, since it's more accurate?" — a cross-encoder has no way to precompute anything; every document would need to be re-encoded jointly with every new query, at query time, across the entire corpus. That's computationally infeasible past a few thousand documents — hence the two-stage design: cheap bi-encoder retrieval narrows millions down to dozens, then the expensive cross-encoder only has to score that small shortlist.

Worked example: cross-encoder re-ranking corrects a false positive

Continuing the paraphrase-query example from §06 — hybrid retrieval's top 3 were docs [1], [12], [9]. Casting a slightly wider net (top 6 candidates) and re-ranking with a cross-encoder ( cross-encoder/ms-marco-MiniLM-L-6-v2) gives:

Before re-ranking (hybrid RRF order) After cross-encoder re-ranking
1st [1] "Employees are entitled to 15 days of paid annual leave..." [1] relevance = −0.909
2nd [12] "Remote employees receive a one-time $500 stipend..." [9] relevance = −0.964
3rd [9] "New employees complete a 90-day probationary period..." [0] relevance = −8.505
Doc [12] — the $500 stipend document — got demoted out of the top 3 entirely. It shares surface vocabulary with the query ("employees", "new hires"-adjacent phrasing), which is why hybrid retrieval ranked it 2nd — but a stipend has nothing to do with "how much time off." The cross-encoder, which actually reads the query and document together instead of comparing pre-computed vectors, correctly judges it far less relevant than [9] (the probationary-period document, which really is about a new-hire timeline).
Notice the score gap: [1] and [9] land close together (−0.909 vs. −0.964), but [0] (the general return-policy document, pulled in only because the wider net of 6 candidates included it) scores −8.505 — nearly 8 points lower. The absolute magnitude isn't meaningful on its own (these are raw, uncalibrated logits), but a gap this large is the cross-encoder saying, in effect: "the first two are genuinely about the question; this third one isn't — it's just the best of a weak remaining field."
Section 08

RAG Evaluation

RAG has two components that can each independently fail — retrieval and generation — so evaluation needs metrics for both, plus metrics for how well they work together.

Layer Metric Question it answers
Retrieval Recall@k Is the relevant document among the top k retrieved?
MRR (Mean Reciprocal Rank) How high does the first relevant document rank, on average? (1/rank, averaged)
Generation Faithfulness / groundedness Is every claim in the answer actually supported by the retrieved context?
Answer relevance Does the answer actually address the question asked?
End-to-end Context precision/recall Of the retrieved chunks, how many were actually needed — and were any needed ones missing?
Why "faithfulness" is checked separately from correctness: an answer can be factually true but unfaithful — right by coincidence, not because the retrieved context actually supported it (the LLM's own parametric knowledge answered it instead). RAG evaluation frameworks (e.g. RAGAS) specifically test this by checking whether each generated claim can be traced back to a sentence in the retrieved context, independent of whether the claim happens to be true.

1. Recall@k, worked on 10 real labeled queries

The lab notebook's 10-query labeled set, run through BM25 with k=3. Real per-query hit/miss:

// query → gold doc id → BM25's actual top-3 → hit? "How long is the return window?" → gold=0 → top3=[0,6,15] → HIT "How much vacation time do I get?" → gold=1 → top3=[12,15,14] → MISS "What's the battery size on the X-450?" → gold=2 → top3=[11,2,8] → HIT "How do I change my password?" → gold=3 → top3=[3,15,14] → HIT "How fast does the X-450 charge?" → gold=4 → top3=[4,5,8] → HIT "Does sick leave need advance notice?" → gold=5 → top3=[5,1,15] → HIT "How long do refunds take to process?" → gold=6 → top3=[6,3,4] → HIT "What's the response time for a critical support ticket?" → gold=7 → top3=[7,12,11] → HIT "What resolution is the X-450 screen?" → gold=8 → top3=[8,13,2] → HIT "How long is the probation period for new hires?" → gold=9 → top3=[9,11,13] → HIT Recall@3 = 9 hits / 10 queries = 90.0% ← exactly what the notebook prints
The one miss is instructive: "vacation time" retrieves docs about remote-work stipends and price matching — zero mention of the actual annual-leave document (id 1) anywhere in the top 3. This is BM25's paraphrase blind spot from §02/§06 showing up directly in a hard metric, not just an anecdotal example.

2. MRR, worked on the same 10 queries

Recall@3 only asks "did it appear in the top 3", treating rank 1 and rank 3 as equally good. MRR keeps the rank information:

// reciprocal rank per query (using top-5, so the miss above still gets 0 since it's absent even at k=5) rank 1 → 1/1 = 1.000 (7 of the 10 queries land the gold doc at rank 1) rank 2 → 1/2 = 0.500 ("battery size" — BM25 ranks doc 11 above doc 2) not found in top-5 → 0.000 ("vacation time") MRR = (1.000×8 + 0.500×1 + 0.000×1) / 10 = 8.500 / 10 = 0.850 ← matches the notebook exactly
Recall@3 (90%) and MRR (0.850) tell related but different stories from the same data. Recall@3 says "1 total failure out of 10." MRR additionally docks a fraction of a point for the "battery size" query, which technically succeeded (doc 2 is in the top 3) but only at rank 2 — a real, if smaller, quality gap that Recall@3 is blind to.

3. Faithfulness / groundedness

The lab notebook's actual LCEL chain answer for "How much time off do new hires get each year?", checked claim-by-claim against its retrieved context (doc 1: "Employees are entitled to 15 days of paid annual leave per calendar year, accruing monthly."):

// Real generated answer: "New employees receive 15 days of paid annual leave per calendar year." Claim 1: "15 days" → traceable to context → faithful Claim 2: "paid annual leave" → traceable to context → faithful Claim 3: "per calendar year" → traceable to context → faithful // Every claim traces back to the retrieved sentence -> fully faithful // A hypothetical UNFAITHFUL variant of the same answer: "New employees receive 15 days of paid annual leave per calendar year, and up to 5 unused days carry over into the following year." Claim 4: "5 unused days carry over" → NOT in any retrieved chunk → unfaithful
Claim 4 might even be true (plenty of real leave policies do allow carryover) — faithfulness doesn't check truth, it checks provenance. An answer scores low on faithfulness the moment it asserts something the retrieved context never said, regardless of whether that assertion happens to be correct.

4. Answer relevance

Same question, three candidate answers — each grounded in a real document from the corpus, which is exactly what makes this metric necessary:

Candidate answer Faithful? Relevant?
A: "New employees receive 15 days of paid annual leave per calendar year." Yes (doc 1) Yes — directly answers the question
B: "Refunds are processed within 5-7 business days after the item is received." Yes (doc 6) No — perfectly faithful to a real document, but about refunds, not leave
C: "I don't have that information." Yes (vacuously) No — safe, ungrounded-in-nothing-wrong, but answers nothing
Answer B is the case faithfulness alone cannot catch. It is 100% traceable to a real retrieved chunk — a retrieval bug (the wrong document got pulled in) rather than a generation bug produced it, and faithfulness checking would score it perfectly. Only answer relevance, which compares the answer against the question rather than against the context, catches that it's simply off-topic.

5. Context precision & recall

For the same query, hybrid retrieval + re-ranking (§06-§07) returned three chunks: [1] (annual leave — actually used to generate the answer), [9] (90-day probation — topically close, but not used), [0] (general return policy — pulled in only by the wider candidate net, not used):

// Of the 3 retrieved chunks, only 1 was actually necessary to produce the answer Context precision = necessary chunks retrieved / total chunks retrieved = 1 / 3 = 0.33 // Of the 1 chunk actually necessary to fully answer this question, all 1 were retrieved Context recall = necessary chunks retrieved / total necessary chunks that exist = 1 / 1 = 1.00
Perfect recall, mediocre precision — a very common real pattern. Nothing needed for the answer was missed (recall = 1.0), but two-thirds of the context budget spent on this question was, in retrospect, unnecessary. This is precisely the "over-retrieval dilution" failure mode in §09 — a context window can score perfectly on recall while still being 67% noise.
Section 09

Retrieval Failures

Failure mode What happens Mitigation
Missing context The answer requires information that was never indexed at all Corpus coverage audit; explicit "I don't know" fallback rather than guessing
Irrelevant retrieval Top-k chunks look similar by embedding but don't actually answer the question Re-ranking (§07); tighter similarity thresholds; better chunking (§05)
Lost-in-the-middle LLMs attend less reliably to information placed in the middle of a long context window than at the start or end Put the most relevant chunk first/last; keep retrieved context concise rather than maximal
Redundant retrieval Top-k chunks are near-duplicates of each other, wasting context budget Diversity-aware re-ranking (e.g. Maximal Marginal Relevance)
Over-retrieval dilution Too many chunks retrieved "just in case," burying the genuinely relevant one Tune k down; rely on re-ranking to do the real filtering, not raw retrieval volume
The unifying theme: nearly every retrieval failure is really a signal-to-noise problem in the context window — too little of the right information, too much of the wrong information, or the right information placed where the model attends to it least. §08's evaluation metrics exist specifically to catch these before they reach users.

1. Missing context — real example

The lab notebook's own SS09 demonstration: "Who is the company's CEO?", asked of a 16-document corpus that contains no information about a CEO at all.

// Real retrieval output — retrieval ALWAYS returns its top-k, however irrelevant: "The company's return policy allows returns within 30 days of purchase with a valid receipt." "Model X-450's screen is 6.5 inches with a resolution of 2400x1080." "Remote employees receive a one-time $500 home office setup stipend." // Real generated answer: "The company's CEO is not explicitly mentioned in the given context... it is impossible to determine who the company's CEO is."
This is the failure mode working correctly, not incorrectly. Retrieval did the only thing it can do — return its nearest matches — and generation's grounding instruction (§04, §07) caught that none of them were actually relevant. The "fix" here isn't better retrieval, since no chunk in the corpus could ever answer this; it's making sure the LLM says so instead of guessing from its own training data.

2. Irrelevant retrieval — real example

The same paraphrase query from §06/§07, run through the local generation model with two different contexts: the raw hybrid-RRF order (before re-ranking, includes the irrelevant stipend document) vs. the cross-encoder re-ranked order.

// BEFORE re-ranking — context = [doc 1 (leave policy), doc 12 (stipend), doc 9 (probation)] Question: "How much time off do new hires get each year?" Answer: "New employees receive 90 days of paid annual leave each year." ← WRONG // AFTER re-ranking — context = [doc 1 (leave policy), doc 9 (probation), doc 0 (return policy)] Answer: "New employees receive 15 days of paid annual leave per calendar year." ← correct
The correct chunk (doc 1, "15 days") was present in BOTH contexts. Irrelevant retrieval didn't just waste space — the model appears to have blended the "90-day probationary period" number from the noise document into its answer about leave, producing a confident, wrong, oddly specific number. This is a real, reproducible failure: having the right chunk in context is necessary but not sufficient if the wrong chunks are sitting right next to it.

3. Lost-in-the-middle — a real attempt, and why it didn't reproduce here

Placed a chunk containing a specific fact ("Remote employees receive a one-time $500 home office setup stipend.") at the start, middle, and end of a 16-chunk context, and asked the local model for that exact fact each time:

Correct chunk at position 1 of 16: "...home office setup stipend is $500." ✓ Correct chunk at position 8 of 16: "...home office setup stipend is $500." ✓ Correct chunk at position 16 of 16: "...home office setup stipend is $500." ✓ // No degradation observed at any position, in this setup
Honest result: this local, small-scale setup did not reproduce the effect. Liu et al. (2023)'s original finding uses much longer contexts (tens of retrieved passages, thousands of tokens) and often several plausible-looking distractor values competing for the same answer slot — conditions this 16-short-sentence, single-unambiguous-fact setup doesn't create. The lesson isn't "lost-in-the-middle isn't real" — it's that the effect is a function of context length and distractor difficulty, and a demo has to actually stress those to show it. Take this as a template to stretch (more chunks, longer chunks, near-duplicate decoy numbers) rather than as a disproof.

4. Redundant retrieval — worked with real embeddings

A real embedding computation: candidate A (the genuine ticket-priority document) and candidate B (a synthetic near-duplicate paraphrase of A), alongside two unrelated real documents, all scored against the query "What are the support ticket priority levels?":

// Real cosine similarities sim(query, A) = 0.854 sim(query, B) = 0.700 sim(query, C) = 0.198 sim(query, D) = 0.229 sim(A, B) = 0.810 ← A and B are near-duplicates of each other // Relevance-only ranking would pick: A, B, D — wasting slot 2 on a near-duplicate of slot 1 // MMR (λ=0.5) selection trace: step 1: pick A (highest relevance, nothing selected yet to penalize) step 2: MMR(B) = 0.5×0.700 − 0.5×0.810(sim to A) = −0.055 MMR(D) = 0.5×0.229 − 0.5×0.264(sim to A) = −0.018 ← wins, D picked instead of B step 3: pick C (last remaining) MMR final order: A, D, C ← B (the redundant paraphrase) never gets a context slot
MMR didn't drop B because it's irrelevant — sim(query, B) = 0.700 is still fairly high. It dropped B because, having already selected A, adding B contributes almost nothing new: the marginal value of a near-duplicate is low regardless of how relevant it looks in isolation. That's the "marginal" in Maximal Marginal Relevance.

5. Over-retrieval dilution — a real recall@k curve

BM25 recall@k over the notebook's 10 labeled queries, k = 1 through 10:

k= 1 Recall@k = 80.0% k= 2 Recall@k = 90.0% ← the only real gain past k=1 k= 3 Recall@k = 90.0% k= 4 Recall@k = 90.0% k= 5 Recall@k = 90.0% ... // flat all the way out k=10 Recall@k = 90.0% ← identical to k=2
Every chunk retrieved beyond k=2 bought exactly zero additional recall on this query set, while still consuming context-window budget and giving the LLM 5-8 more chances to be distracted by something irrelevant (exactly failure mode #2, above). "Retrieve more, just in case" is not a free hedge — past the point where recall saturates, it's pure downside.
Section 10

Knowledge Freshness

The index built in §04's "index-time" phase is a snapshot. The moment the underlying documents change — a policy updates, a price changes, a new document is added — that snapshot is stale, and RAG will confidently retrieve and ground answers in outdated information.

Strategy How it works Trade-off
Full re-index Periodically re-embed and rebuild the entire index from scratch Simple, guaranteed consistent; expensive and slow at scale
Incremental indexing Only re-embed documents that actually changed (tracked via timestamps/hashes); add/update/delete individual vectors Cheap and fast; requires change-tracking infrastructure
Time-decay scoring Down-weight older documents in the ranking, even if not literally removed Softens staleness without needing to detect exact changes; needs reliable timestamps
A freshness failure looks exactly like a correct RAG answer. The system will retrieve confidently, generate a well-grounded-sounding answer, cite a real chunk — and the chunk itself is just outdated. This makes freshness bugs unusually dangerous: there's no error to catch, only a wrong answer delivered with full apparent legitimacy.

1. Full re-index — worked cost

A corpus of 50,000 documents, each taking ~8ms to embed (a realistic small sentence-embedding model on CPU), where only 12 documents actually changed since yesterday:

Full re-index cost = 50,000 docs × 8ms = 400,000ms = 400 seconds (~6.7 minutes) // ...to account for 12 changed documents out of 50,000 (0.024% of the corpus)
The waste scales with corpus size, not with how much actually changed. At 50,000 documents this is an annoying 7-minute batch job; at 50 million it's the difference between a nightly job and one that never finishes before the next day's changes arrive.

2. Incremental indexing — the same scenario, done differently

Incremental re-index cost = 12 changed docs × 8ms = 96 milliseconds Speedup = 400,000ms / 96ms ≈ 4,167x fewer embedding calls // Plus: delete the 12 old vectors from the index and upsert the 12 new ones — no full rebuild
The 4,167x isn't a rounding trick — it's the literal ratio of "12" to "50,000." The entire cost of incremental indexing comes from change-tracking infrastructure (knowing which 12 changed, out of 50,000, without re-checking all 50,000) — once that's solved, the embedding cost itself becomes nearly free.

3. Time-decay scoring — worked reordering

Two documents competing for the same query: doc X is a strong topical match but 400 days old; doc Y is a weaker match but only 10 days old. Applying exponential decay score = similarity × e^(−λ × age_days) with a moderate decay rate λ = 0.002 (a ~347-day half-life):

// Before decay — pure similarity ranking doc X: similarity = 0.85, age = 400 days ← ranks #1 on similarity alone doc Y: similarity = 0.78, age = 10 days ← ranks #2 on similarity alone // After decay: decayed(X) = 0.85 × e^(−0.002×400) = 0.85 × 0.4493 = 0.382 decayed(Y) = 0.78 × e^(−0.002× 10) = 0.78 × 0.9802 = 0.765 // Y now ranks #1 — the ranking flipped entirely
λ = 0.002/day is a real tuning knob, not a fixed constant — it sets a ~347-day half-life ( ln(2)/λ), meaning a document's effective score halves roughly every 11.5 months regardless of how well it originally matched. Set λ too high and genuinely evergreen content (a well-written policy that hasn't changed in years) gets unfairly buried; set it too low and staleness stops mattering at all. Unlike full or incremental re-indexing, this strategy never requires detecting that content changed — it just assumes older is progressively less trustworthy by default.
Section 11

Retrieval Security Considerations

Risk Mechanism Mitigation
Indirect prompt injection A malicious instruction hidden inside a retrieved document ("ignore previous instructions and...") gets fed into the LLM's context as if it were trusted data, and the model may follow it Treat retrieved content as untrusted data, never as instructions; sanitize/strip suspicious patterns; instruction-hardened prompting
Data leakage across access boundaries A shared vector index retrieves a chunk the querying user shouldn't be permitted to see (wrong tenant, wrong permission level) Metadata-based access filtering enforced at retrieval time, not just at the UI layer
Corpus/index poisoning An attacker with write access to the source documents inserts content specifically crafted to be retrieved for common queries and to manipulate the model's answer Access control on ingestion, not just on query; provenance tracking for indexed content
Embedding inversion Under some conditions, embeddings can leak information about the original text they were computed from Treat embeddings themselves as sensitive data, not just the raw documents
Exam favourite: "Why is prompt injection via retrieved documents different from the prompt injection risks in earlier modules?" — the injected instruction doesn't come from the user's own prompt, where at least the user is a somewhat-trusted party — it arrives silently, embedded in data the system itself decided to retrieve and trust, from a document the end user never wrote and often can't even see.
Section 12

Key Takeaways & Exam Prep

✓

Embeddings encode meaning as geometry

Cosine similarity compares direction, not magnitude — the basis for all retrieval in this module.

✓

FAISS trades exactness for speed

Flat is exact but slow at scale; IVF/HNSW/PQ approximate, at a tunable recall cost.

✓

RAG has two distinct phases

Index-time (once) vs. query-time (every request) — confusing them is the most common design mistake.

✓

Chunk size is a real hyperparameter

No universal right answer — tune against your own evaluation set.

✓

Hybrid retrieval fuses disjoint failure modes

Dense catches paraphrase; sparse (BM25) catches exact identifiers.

✓

Re-ranking is a second, more expensive pass

Cross-encoders are too slow for the whole corpus, but affordable on a narrowed shortlist.

✓

Faithfulness ≠ correctness

A RAG answer can be true without actually being grounded in what was retrieved.

✓

Freshness bugs look like correct answers

Nothing errors — the system just confidently grounds you in outdated information.

✓

Retrieved content is untrusted input

Indirect prompt injection arrives through data the system chose to trust, not through the user.

Common exam questions

Question Short answer
Why use a dedicated embedding model instead of an LLM's own token embeddings for retrieval? Token embeddings are optimized for next-token prediction; sentence-embedding models are trained with a contrastive objective specifically so that semantically similar texts land close together
What's the difference between a bi-encoder and a cross-encoder? A bi-encoder embeds query and document separately (allowing pre-computation, used for fast retrieval); a cross-encoder embeds them jointly (more accurate, too slow for anything but re-ranking a short list)
Why combine dense and sparse retrieval instead of picking one? Their failure modes are largely disjoint — dense misses exact identifiers, sparse misses paraphrase — so fusing rankings (e.g. via RRF) recovers documents either alone would miss
What does "faithfulness" measure in RAG evaluation, specifically? Whether every claim in the generated answer is actually traceable to the retrieved context — independent of whether the claim happens to be true
Why is indirect prompt injection via retrieved documents especially dangerous? The malicious instruction arrives as data the system itself chose to trust and insert into context, not from the user's own (at least partially trusted) prompt
