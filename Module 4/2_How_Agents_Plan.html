How Agents Plan

Section 01

Planning & the Two Families of Planners

Planning is the problem of finding a sequence of actions that transforms an initial state into a goal state. Every planning problem has the same four ingredients:

1

Initial state

A complete description of the world before any action is taken.

2

Actions

Operators that transform one state into another, each with conditions for when it applies.

3

Goal state

A description of what must be true when the plan finishes (often partial, not a full state).

4

Plan

An ordered sequence of actions connecting initial → goal, found by search.

Recap from Part 1, Section 03: a goal-based agent is type 3 on the Russell & Norvig ladder. Unlike a reflex agent, it holds an explicit goal, predicts what each action would lead to, and picks actions that make the goal reachable. Part 1 explains what this agent type is. This Part explains how it decides: by planning.

FIG 1 — A reflex agent has no notion of "why" — the rule fires or it doesn't. A goal-based agent explicitly evaluates candidate actions against how much closer they get it to a stated goal, which is what makes search (Section 03) meaningful in the first place.

The two families of planning

A goal-based agent can plan in two main ways. What separates them is how a state is represented, and that choice decides which search technique and which action description you can use.

Family 1: Goal-based (search) planningFamily 2: Classical (STRIPS) planning
StateAtomic: a black-box label, e.g. In(Arad)Factored: a set of logical facts, e.g. {On(C,A), Clear(B), HandEmpty}
ActionsA successor function Result(s,a), looked up in a map or graphSTRIPS schemas with PRE / ADD / DEL lists the planner can inspect
How the plan is foundState-space graph search: BFS, DFS, A*State-space search over fact sets: forward (progression) or backward (regression)
HeuristicHand-crafted for each problem (e.g. straight-line distance)Can be derived automatically from the schemas (e.g. count unsatisfied goal facts, ignore delete lists)
GeneralityOne formulation per problemDomain-independent: one planner solves any problem written in STRIPS/PDDL
EnvironmentAny (search also extends to stochastic and partially observable settings)Fully observable, deterministic, static, discrete (Section 04)

One-line exam answer: classical planning is goal-based planning. Both search for an action sequence that reaches a goal. The difference is that in Family 1, a state like In(Arad) is a closed box. In Family 2, the state is opened up into logical facts and the actions are described in STRIPS, which lets a single general-purpose planner reason about any problem. State-space search is used in both. Family 1 searches a graph of labels; Family 2 searches over sets of facts.
Planning vs. reactive response: a purely reactive agent (Part 1, Section 04) maps the current observation directly to an action — no lookahead. A planner explicitly reasons about the consequences of actions before committing, searching several steps ahead before acting even once. This lookahead-before-acting distinction reappears in the plan-and-execute strategy (Section 09).
Where this connects to LLM agents: Part 1 (Section 04) places this agent type in the deliberative family. An LLM agent prompted with a goal and asked to plan its own steps (ReAct and plan-and-execute, Sections 08–09) is a goal-based agent in this exact classical sense — just with a language model doing the "compare to goal" reasoning instead of hand-coded symbolic logic.

Section 02 · Family 1

Problem Formulation with Atomic States

In Family 1, the agent treats each state as an indivisible label. It can only ask two things: "which states can I reach from here?" and "is this the goal?". The classic example is route finding.

Worked example — route finding with atomic states (Arad → Bucharest)

This is the classic goal-based agent from Russell & Norvig. A tourist in Arad, Romania, has a flight out of Bucharest tomorrow and needs the shortest driving route.

FIG 2 — Part of the Romania road map (Russell & Norvig). Grey numbers are road distances in km. Orange numbers are the straight-line distance to Bucharest, which is the heuristic h(n). The green route is the optimal path, 418 km.

Problem formulation. Each state is just the name of a city. That's what atomic means.

ActionsActions(In(Arad)) = { Go(Sibiu), Go(Timisoara), Go(Zerind) }
Transition modelResult(In(Arad), Go(Sibiu)) = In(Sibiu). This is a lookup in the road map, not a rule the agent can inspect.

Heuristich(n) = straight-line distance to Bucharest. This is extra knowledge supplied from outside (it comes from geography, not from the state).
Section 03 · Family 1

State Space Search

Once a problem is framed as "find a path from initial state to goal state," it becomes a graph search problem: states are nodes, actions are edges. Classical planning is, at its core, an application of search algorithms to this graph.

AlgorithmStrategyGuarantees
BFS (Breadth-First Search)Explore all states at depth d before depth d+1Finds the shortest plan (fewest actions), but memory-expensive
DFS (Depth-First Search)Follow one branch as deep as possible before backtrackingMemory-efficient, but can find a needlessly long plan first
A\* SearchBest-first search guided by f(n) = g(n) + h(n) — cost so far plus a heuristic estimate to the goalFinds the optimal plan, IF the heuristic never overestimates true cost (admissible)
// A* evaluation function — the heuristic is what makes it smarter than plain BFS f(n) = g(n) + h(n) // g(n) = actual cost of the path from start to node n (known exactly) // h(n) = ESTIMATED cost from n to the goal (a heuristic guess) // A* expands the node with lowest f(n) first — cheapest so far + most promising remaining

Worked example — BFS vs. DFS vs. A* on one graph

FIG 3 — Start S, goal G. Numbers on edges are action costs, and h is the heuristic estimate to G. The green path S→A→C→G (cost 5) is optimal. h is admissible: it never exceeds the true remaining cost (S:5, A:4, B:5, C:3).
// BFS — FIFO queue, successors in alphabetical order expand S → frontier [A, B] expand A → frontier [B, C, G] // G reached at depth 2 result: S → A → G 2 actions, cost 13 // fewest ACTIONS, not cheapest // DFS — LIFO stack, always dive into the first successor S → A → C → G result: S → A → C → G cost 5 // lucky: depends on successor order. // If A tried G before C, DFS returns cost 13 // A* — expand lowest f = g + h expand S (f=0+4=4) → A: f=1+4=5 B: f=4+4=8 expand A (f=5) → C: f=2+3=5 G: f=13+0=13 expand C (f=5) → G: f=5+0=5 // cheaper path to G found, so update it expand G (f=5) → GOAL result: S → A → C → G cost 5 (optimal) // B was never expanded: the heuristic pruned it

Worked example — A* on the Romania map (Section 02)

// A* from Arad (f = g + h, always expand the lowest f) expand Arad (366) → Sibiu 140+253=393 Timisoara 118+329=447 Zerind 75+374=449 expand Sibiu (393) → Rimnicu 220+193=413 Fagaras 239+176=415 Oradea 291+380=671 expand Rimnicu (413) → Pitesti 317+100=417 Craiova 366+160=526 expand Fagaras (415) → Bucharest 450+0=450 // a route to the goal, but not yet the cheapest expand Pitesti (417) → Bucharest 418+0=418 // cheaper route to Bucharest found, so update it expand Bucharest (418) → GOAL ✓ plan: Go(Sibiu) → Go(Rimnicu Vilcea) → Go(Pitesti) → Go(Bucharest) 418 km // Greedy best-first (h only) would take Sibiu → Fagaras → Bucharest = 450 km: fast to find, but not optimal
Exam favourite: "Why does A* need an admissible heuristic to guarantee optimality?" — if h(n) ever overestimates the true remaining cost, A* can be tricked into abandoning a node that was actually on the optimal path, in favor of one that only looked cheaper. Admissibility (never overestimating) guarantees the algorithm never prunes away the true optimal solution.
This is why "search" and "reasoning" are related words in this course. Tree-of-Thoughts (Module 2 Part 2 Section 01) is state-space search with an LLM as both the successor-generator and the heuristic evaluator — the exact same BFS/best-first machinery from this section, just operating over "partial reasoning states" instead of classical planning states.

Section 04 · Family 2

Classical Planning: Factored States

Family 2 opens up the state. Instead of a label, a state is a set of facts that are true in the world, and actions say exactly which facts they need and which they change. This is classical planning.

Atomic vs. factored: the step from Family 1 to Family 2

Atomic (Romania)Factored (Blocks World, below and Section 05)
A state looks likeIn(Sibiu), a single label{On(C,A), OnTable(A), OnTable(B), Clear(C), Clear(B), HandEmpty}
What the agent can ask of a stateOnly "is this the goal?" (yes or no)"Which goal facts are already true, and which are missing?"
How close is In(Pitesti) to the goal?The state can't tell you. You need an external table of straight-line distances.The state tells you: count the unsatisfied goal facts. On(A,B) is missing, so the state is "1 fact away".
Where actions come fromA road map: Result(s,a) is a black-box lookupSTRIPS schemas: PRE / ADD / DEL that a planner can reason about
ConsequenceYou need a problem-specific search plus a hand-made heuristicA domain-independent planner can derive its own heuristics and solve any problem written in STRIPS
Key insight: the Romania agent and the Blocks World planner are both goal-based. Both search for a sequence of actions that reaches a goal. The difference is that in Romania, In(Arad) is a closed box. In Blocks World, the state is opened up into logical facts. That one change in representation is what turns "goal-based search" into "classical planning".

Worked example — the four ingredients for a 3-block problem

This one problem is reused in Section 05 and Section 06, so you can follow the same task from problem statement, to STRIPS encoding, to a finished plan.

FIG 4 — The "Sussman anomaly" problem. It looks trivial, but you can't solve it by completing one goal fact at a time. Section 06 shows why.
IngredientFor this problem
Initial stateOn(C,A) ∧ OnTable(A) ∧ OnTable(B) ∧ Clear(C) ∧ Clear(B) ∧ HandEmpty, a complete list of what is true. Any fact not listed is false (the closed-world assumption).
ActionsPickup(x), Putdown(x), Stack(x,y), Unstack(x,y): a robot hand that holds one block at a time (written out in STRIPS in Section 05).
GoalOn(A,B) ∧ On(B,C). This is partial: it doesn't say whether the hand is empty or what is clear.
PlanUnstack(C,A) → Putdown(C) → Pickup(B) → Stack(B,C) → Pickup(A) → Stack(A,B) (6 actions)

AssumptionMeaningExample of breaking it

Section 05 · Family 2

STRIPS: Describing Actions

STRIPS (Stanford Research Institute Problem Solver, 1971) is the classical formal language for representing planning actions — precise enough that a program can search over it automatically. Its core idea: represent each action by what it requires and what it changes.

// A STRIPS action has three parts Action: Pickup(block) Precondition: Clear(block) ∧ OnTable(block) ∧ HandEmpty Add list: Holding(block) // facts made TRUE by this action Delete list: OnTable(block), HandEmpty, Clear(block) // facts made FALSE // A plan is valid if, applying each action's add/delete list in order, // every action's precondition holds in the state that precedes it, // and the final state satisfies the goal.

Worked example — the classic Blocks World

FIG 5 — Two STRIPS actions chained into a plan. Pickup(A) requires Clear(A) ∧ HandEmpty and produces Holding(A) while deleting HandEmpty; Stack(A,B) requires Holding(A) ∧ Clear(B) and produces On(A,B) — the plan is valid because each action's precondition is satisfied by the state the previous action's add/delete lists produced.

The complete Blocks World operator set

These are the four actions used to solve the 3-block problem from Section 04, all written in STRIPS:

Pickup(x) // lift x from the table PRE: Clear(x) ∧ OnTable(x) ∧ HandEmpty ADD: Holding(x) DEL: OnTable(x), Clear(x), HandEmpty Putdown(x) // place the held block on the table PRE: Holding(x) ADD: OnTable(x), Clear(x), HandEmpty DEL: Holding(x) Unstack(x, y) // lift x off the top of y PRE: On(x,y) ∧ Clear(x) ∧ HandEmpty ADD: Holding(x), Clear(y) DEL: On(x,y), Clear(x), HandEmpty Stack(x, y) // put the held block x on top of y PRE: Holding(x) ∧ Clear(y) ADD: On(x,y), Clear(x), HandEmpty DEL: Holding(x), Clear(y) // Applying an action: Result(s, a) = (s − DEL(a)) ∪ ADD(a) only if PRE(a) ⊆ s // Any fact not in ADD or DEL is left unchanged. This is how STRIPS sidesteps the "frame problem".
Why STRIPS still matters in an LLM-agent course: modern tool-calling schemas (Part 3, Section 02; Module 2 Section 04.2) are structurally identical to STRIPS operators — a tool has a signature (its "precondition": required arguments and types) and an effect (what changes once it's called). Frameworks like PDDL (STRIPS' modern successor) are even used today to give LLM planners a formally verifiable planning layer underneath their natural-language reasoning.
Section 06 · Family 2

Searching the STRIPS State Space: Forward & Backward

Once the actions are written in STRIPS, the planner builds the state space as it goes: each node is a set of facts, and each edge is an action that can be applied. As in Section 03, it is still state-space search, but now there are two directions to search in.

Forward (progression) searchBackward (regression) search
Starts fromThe initial stateThe goal
Each stepApply any action whose preconditions hold → a new concrete stateChoose an action that achieves part of the goal → a new sub-goal (a set of states)
Stops whenThe current state satisfies the goalThe sub-goal is satisfied by the initial state
StrengthSimple; every state it visits is a real, valid stateOnly considers relevant actions, so it branches less
WeaknessBranches on many irrelevant actions (e.g. shuffling blocks that don't matter)Works with partial states, which makes heuristics harder to design

Forward (progression) search on the 3-block problem

Start from the initial state and apply actions until the goal On(A,B) ∧ On(B,C) holds:

S0: {On(C,A), OnTable(A), OnTable(B), Clear(C), Clear(B), HandEmpty} │ Unstack(C,A) DEL On(C,A), Clear(C), HandEmpty ADD Holding(C), Clear(A) S1: {OnTable(A), OnTable(B), Clear(A), Clear(B), Holding(C)} │ Putdown(C) DEL Holding(C) ADD OnTable(C), Clear(C), HandEmpty S2: {OnTable(A), OnTable(B), OnTable(C), Clear(A), Clear(B), Clear(C), HandEmpty} │ Pickup(B) DEL OnTable(B), Clear(B), HandEmpty ADD Holding(B) S3: {OnTable(A), OnTable(C), Clear(A), Clear(C), Holding(B)} │ Stack(B,C) DEL Holding(B), Clear(C) ADD On(B,C), Clear(B), HandEmpty S4: {OnTable(A), OnTable(C), On(B,C), Clear(A), Clear(B), HandEmpty} │ Pickup(A) DEL OnTable(A), Clear(A), HandEmpty ADD Holding(A) S5: {OnTable(C), On(B,C), Clear(B), Holding(A)} │ Stack(A,B) DEL Holding(A), Clear(B) ADD On(A,B), Clear(A), HandEmpty S6: {OnTable(C), On(B,C), On(A,B), Clear(A), HandEmpty} // ✓ goal satisfied

Backward (regression) search on the same problem

Start from the goal. Choose an action that adds a goal fact and deletes none of them. Then replace the goal with what must have been true before that action:

// Regression: g' = (g − ADD(a)) ∪ PRE(a) G0: {On(A,B), On(B,C)} │ regress through Stack(A,B) // adds On(A,B) ✓ G1: {On(B,C), Holding(A), Clear(B)} │ regress through Pickup(A) // adds Holding(A) ✓ G2: {On(B,C), Clear(B), Clear(A), OnTable(A), HandEmpty} │ regress through Stack(B,C) // adds On(B,C) ✓ G3: {Clear(A), OnTable(A), Holding(B), Clear(C)} │ regress through Pickup(B) // adds Holding(B) ✓ G4: {Clear(A), OnTable(A), Clear(B), OnTable(B), Clear(C), HandEmpty} │ regress through Putdown(C) // adds Clear(C), HandEmpty ✓ G5: {Clear(A), OnTable(A), Clear(B), OnTable(B), Holding(C)} │ regress through Unstack(C,A) // adds Holding(C), Clear(A) ✓ G6: {OnTable(A), OnTable(B), Clear(B), On(C,A), Clear(C), HandEmpty} G6 ⊆ S0 → stop. Read the actions bottom-to-top → the same 6-step plan
Why this example is famous (the Sussman anomaly): try to solve the goals one at a time and you fail. If you achieve On(A,B) first (move C off A, then stack A on B), you have to pull A back off to get B onto C. If you achieve On(B,C) first (C is still sitting on A), you build the tower B–C–A, and A is buried at the bottom, so you have to take the tower apart. No order of "finish goal 1, then goal 2" works. The planner has to interleave the subgoals, which is what the 6-step plan above does. This exposed the limits of early linear planners and led to partial-order planning.

Section 07

From Classical Planning to LLM Planning

Every ingredient of classical planning survives in an LLM agent. What changes is how much the agent knows before it starts.

IngredientClassical planner (Sections 01–06)LLM agent
StateA label or a set of logical factsThe conversation so far: the request, previous thoughts and tool results, in natural language
ActionsSTRIPS operators with PRE / ADD / DELTools described by a name, a description and a JSON schema (Part 3)
Transition modelKnown in advance: Result(s,a) is computableUnknown: the agent only learns what a search or API returns by actually calling it
GoalA logical formula, e.g. On(A,B) ∧ On(B,C)A task in natural language, e.g. "summarise this week's incidents"
SearchAn explicit algorithm (BFS, A*, regression)The model's own reasoning, optionally wrapped in an explicit search (Section 11)
WorldClosed, deterministic, fully observableOpen, uncertain, partly observable
The key consequence: because an LLM agent can't predict what a tool will return, it can't compute a whole plan offline the way STRIPS does. It must interleave planning with acting and observing. The four strategies below differ in how far ahead they plan before acting, and in what they do when things go wrong.

Section 08

ReAct: Plan One Step at a Time

ReAct (Yao et al., 2022) interleaves a Thought (reason about what to do next), an Action (a tool call) and an Observation (the tool's result) until the agent can answer. In planning terms it is online planning with one-step lookahead: it never commits to more than the next action.

// Task: "How many days can the Orbital Relay Station keep operating?" (the lab's knowledge base) Thought 1: I need the station's fuel reserve and daily consumption. Action 1: lookup_fact("orbital relay station") Observation 1: 340 units of fuel, consuming 28 units per day. Thought 2: Days = 340 / 28. I should calculate rather than guess. Action 2: calculator("340 / 28") Observation 2: 12.142857 Thought 3: I have what I need. Final Answer: About 12 days (12.1) of normal operation.
Classical conceptReAct's version
PerceptionThe Observation returned by the last tool call
Search / lookaheadOne step: the Thought chooses only the next Action
ReplanningAutomatic: every step re-decides from the latest Observation
ReAct is not "reactive". The names are close but they sit on opposite halves of Part 1's ladder. A reactive agent maps the current input straight to an action with a fixed rule, with no goal and no lookahead. A ReAct agent (Reason + Act) holds a goal, reasons about it, chooses the action expected to move it closer, and re-plans after every observation. That makes it goal-based, i.e. deliberative, though with only one step of lookahead.
ReAct's limitation: with no lookahead it can wander, taking a locally sensible step that turns into a dead end several steps later, and it spends one LLM call per step. Sections 09–11 each fix part of this.
Section 09

Plan-and-Execute: Commit to a Plan First

The plan-and-execute (planner–executor) strategy splits the agent in two. A planner writes the whole multi-step plan up front, like a classical planner. An executor carries it out step by step, and the planner is called again only if a step fails. This is BDI's "intention" from Part 1: commit to a plan, and re-plan only when necessary.

FIG 7 — Unlike ReAct's one-step-at-a-time loop, the planner commits to a full sequence before execution begins — closer to classical planning (Sections 04–06), with the LLM as both planner and (if a step fails) replanner.
ReActPlan-and-execute
LookaheadNone: one step at a timeFull plan before execution
Adapts mid-task?Naturally, every stepOnly on explicit re-planning
LLM callsOne per stepOne plan, then cheap execution; more only on failure
Best forExploratory tasks where the path becomes clear as you goTasks whose overall shape is knowable up front

Section 10

Reflection: Repair the Plan After Failure

Neither ReAct nor plan-and-execute learns from a failed attempt. Reflection adds an evaluate-and-retry loop: after an attempt, the agent (or a separate critic) checks the result, writes a short critique in natural language, and uses it to plan the next attempt. Reflexion (Shinn et al., 2023) keeps these critiques in memory across attempts. It is plan repair driven by feedback.

// Task: write is_prime(n). Checked by unit tests. Attempt 1: returns True for n = 1 ✗ test_one fails Reflection: "1 is not prime. Handle n < 2 before the loop." // stored in memory Attempt 2: adds if n < 2: return False ✓ all tests pass
Reflection works best with an external signal: unit tests, a validator, a tool error or a human rating. Self-critique with no outside check can talk itself into a wrong answer just as confidently. In Part 4 the same loop appears as the evaluator–optimizer workflow pattern; here it is a planning strategy.
Section 11

Tree Search: Explore Several Plans

The most deliberate strategy brings back Section 03's search algorithms, with the LLM doing two jobs: proposing next steps (the successor function) and evaluating partial plans (the heuristic).

MethodSearch usedClassical link
Tree of Thoughts (Yao et al., 2023)Breadth- or depth-first search over partial reasoning steps, with the LLM scoring each branchBFS / DFS from Section 03, with an LLM heuristic
LATS (Zhou et al., 2023)Monte Carlo tree search over actions, with reflection on failed branchesBest-first search plus learning from failures
Cost warning: exploring b branches to depth d can need on the order of b × d LLM calls or more. Use tree search when a wrong answer is expensive and the task has a checkable answer (puzzles, code, maths), not for everyday assistant requests.

Section 13

Key Takeaways & Exam Prep

✓

Planning = search over states

Initial state, actions, goal, and a search to connect them.

✓

Two classical families

Atomic states with graph search; factored states with STRIPS.

✓

A* needs an admissible heuristic

Overestimating can prune away the optimal plan.

✓

LLM agents can't plan fully offline

Tool results are unknown in advance, so they interleave planning and acting.

✓

Four LLM strategies

ReAct, plan-and-execute, reflection, tree search: more deliberation, more cost.

Common exam questions

QuestionShort answer
What are the four components of a planning problem?Initial state, actions (with preconditions and effects), goal, and the plan connecting them
What are the two classical families of planning?Goal-based search over atomic states (BFS, DFS, A*) and classical STRIPS planning over factored states (forward or backward search over fact sets)
Give the STRIPS state-update rule.Result(s,a) = (s − DEL(a)) ∪ ADD(a), applicable only when PRE(a) ⊆ s
Why is A* optimal only with an admissible heuristic?It never overestimates the remaining cost, so A* never discards a node on the optimal path
Why can't an LLM agent plan like STRIPS?Its transition model is unknown: it learns what a tool returns only by calling it, so it must interleave planning, acting and observing
ReAct vs. plan-and-execute?ReAct decides one step at a time and adapts every step; plan-and-execute commits to a full plan first and re-plans only on failure, using fewer LLM calls on predictable tasks
What does reflection add, and what makes it reliable?An evaluate–critique–retry loop that repairs the plan after failure; it is most reliable with an external signal such as tests or a validator
How is Tree of Thoughts related to classical search?It is BFS/DFS over partial reasoning states, with the LLM acting as both successor generator and heuristic
