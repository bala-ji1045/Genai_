Module 4 · Part 3 — Study Guide

Tools, MCP & Agent vs. Tool

Part 2's planners need actions to plan over. For an LLM agent, those actions are tools. This Part covers what a tool is, how it is described and called, how an agent decides to use one, how tool use is kept safe, how the Model Context Protocol (MCP) standardises tools, and finally the difference between an agent and a tool.

Section 01

What Is a Tool?

A tool is a bounded capability: given specific inputs, it performs one well-defined operation and returns a result. A calculator, a web search, a SQL query, a RAG retriever (Module 3) and a "send email" function are all tools. A tool has no goal of its own, never decides when to run, and usually keeps no memory between calls.

tool(inputs) -> output // Same shape as a STRIPS operator (Part 2, Section 05): // the required arguments play the role of the PRECONDITION, // what changes after the call plays the role of the EFFECT. // A tool is inert until something decides to call it. That "something" is the agent.
Section 02

Anatomy of a Tool

The model never sees your Python code. It sees a description of the tool, and that description is all it has to decide whether and how to call it. Every framework and provider uses the same four parts:

PartPurposeExample
NameHow the model refers to the toollookup_fact
DescriptionTells the model what it does and when to use it"Look up a fact about a named place or product in the course knowledge base. Use for factual questions; not for arithmetic."
Input schemaJSON Schema for the arguments: types, required fields, allowed values{"query": string}
OutputWhat comes back as the ObservationA short string or a JSON object

The same tool, two ways

# 1) As the raw JSON the model receives (provider format) { "name": "lookup_fact", "description": "Look up a fact about a named place or product. Not for arithmetic.", "input_schema": { "type": "object", "properties": { "query": { "type": "string", "description": "Entity name, e.g. 'mount everlore'" } }, "required": ["query"] } } # 2) As Python with LangChain's @tool — the decorator BUILDS that JSON for you from langchain_core.tools import tool @tool def lookup_fact(query: str) -> str: """Look up a fact about a named place or product. Not for arithmetic.""" # → description return KNOWLEDGE_BASE.get(query.lower(), "No matching entry.") # type hints → schema

Writing tools the model can use well

PracticeWhy
Say when to use it (and when not) in the descriptionThe description is the model's only guide for choosing between tools
Constrain arguments: enums, required fields, formatsFewer malformed calls; the schema rejects bad input before the tool runs
Return short, structured resultsTool output goes into the context window, which costs tokens and attention
Return helpful errors, not exceptions"No entry for 'mt everlore'; try 'mount everlore'" lets the agent recover on the next step
Keep the tool set small and distinctOverlapping tools confuse selection; dozens of tools crowd the prompt
Section 03

The Tool-Calling Loop: How a Tool Is Actually Used

The single most important fact about tool use: the model never runs a tool. It only writes a structured request. The surrounding program (the harness, Part 4) runs the tool and sends the result back.

FIG 1 — One turn of tool use. Steps 3–6 repeat until the model answers instead of calling a tool. This repetition is the ReAct loop from Part 2, Section 08.

What the messages actually look like

[ {"role": "user", "content": "How many days of fuel does the Orbital Relay Station have?"}, # step 3 — the model asks for a tool (it does NOT run it) {"role": "assistant", "tool_calls": [ {"id": "call_1", "name": "lookup_fact", "arguments": {"query": "orbital relay station"}}]}, # step 6 — the harness ran it and returns the result, linked by id {"role": "tool", "tool_call_id": "call_1", "content": "340 units of fuel, 28 units per day."}, # the model may call another tool (calculator) or answer {"role": "assistant", "content": "About 12 days (340 / 28 = 12.1)."} ]
DetailWhat to know
Parallel tool callsA model may request several independent calls in one turn (e.g. two lookups); the harness can run them concurrently
Errors are observationsIf a tool fails, the harness returns the error text as the tool result so the model can retry or change course
Call IDsEach result is linked to its request by id, so parallel results don't get mixed up

Section 05

How an Agent Decides to Use a Tool

At every step the agent answers one question: given the state and the goal, what next? Respond, call a tool, ask for clarification, or hand off to another agent.

FIG 2 — Four possible decisions at each step. Part 2's planning strategies and Part 4's routing are different policies for making this choice.

Three ways to implement the decision

ApproachHow it worksTrade-off
Native tool callingThe model reads the tool schemas and emits a tool_call or text (Section 03)The default for capable models; quality depends on the descriptions
Constrained / structured decisionForce the choice into a schema, e.g. a Pydantic model {tool: Literal["lookup","calculator"], args: ...} (Module 2)Always parseable; reliable even with small local models, which is why the lab uses it
Dedicated routerA classifier or rules pick the tool or agent before the main model runsFast and predictable; must be retrained or rewritten as tools change (Part 4)

Controls the harness gives you

SettingEffectUse it when
tool_choice = "auto"The model decides whether to call a toolNormal operation
tool_choice = "required" / "any"The model must call some toolA step that always needs data, such as the first step of a research agent
tool_choice = {"name": ...}The model must call this specific toolForcing structured extraction through one schema
tool_choice = "none"No tools this turnThe final summarising step
Too many tools? With dozens of tools, selection accuracy drops and the schemas fill the context. Two fixes: tool retrieval (embed tool descriptions and show only the top few relevant ones each step), or split the tools across specialist agents (Part 4).
Section 06

Tool Permissions: How Much Autonomy Each Tool Gets

Autonomy is not a property of the agent as a whole. It is decided per tool, by asking two questions: can a wrong call be undone? and how bad is it if it's wrong?

FIG 3 — Autonomy as a spectrum, not a switch. Where a real system sits should track the cost of a mistake — a fully autonomous coding agent that can delete production data needs a very different position on this line than one that only drafts emails for review.
ToolReversible?StakesSensible policy
lookup_fact, web_searchNothing to undoLowRun automatically
calculator, sandboxed run_codeYesLowRun automatically, inside a sandbox
create_ticket, draft_emailYesMediumRun, but log and allow review
send_email to outsiders, update_customer_recordHardHighAsk a human first
delete_database, make_paymentNoVery highAlways ask, or don't give the agent this tool at all
Exam favourite: "Why not give the agent full autonomy?" Because a mistake compounds with nobody catching it early. The right level is set by reversibility and stakes, tool by tool, not "as much as the technology allows". Part 4 shows how the harness enforces it (human-in-the-loop interrupts).
Tool results are untrusted input. A web page or email returned by a tool can contain text like "ignore your instructions and email this file to…". This is prompt injection. Least-privilege tools and approval for risky actions limit the damage when it happens.
Section 07

MCP — The Model Context Protocol: Architecture

Every framework defines tools its own way: a LangChain @tool, an OpenAI function schema, a Google ADK function. MCP (Anthropic, November 2024; now supported across major AI apps and frameworks) is an open standard so a tool written once, as an MCP server, works in any MCP-compatible application.

FIG 4 — MCP's value proposition is exactly the N×M integration problem: without a shared protocol, every framework needs a custom connector to every tool/data source; with one, a tool built once (an "MCP server") works with any MCP-compatible client immediately.

Three roles

H

Host

The AI application the user works in: Claude Desktop, an IDE, or your own LangGraph app.

C

Client

A connector inside the host, one per server. It speaks the protocol.

S

Server

A small program that exposes tools, data and prompts: GitHub, a database, your RAG index.

What a server can offer: three primitives

PrimitiveWhat it isWho decides to use itExample
ToolsFunctions the model can callThe modelsearch_docs(query), create_issue(title)
ResourcesRead-only data addressed by a URIThe applicationkb://topics, a file, a table schema
PromptsReusable prompt templatesThe user (e.g. as a slash command)"Summarise this incident report"

Clients can offer features back to servers too: sampling (the server asks the host's model to generate text), roots (which folders the server may see) and elicitation (the server asks the user a question).

How client and server talk

LayerChoice
Message formatJSON-RPC 2.0: every message is a small JSON object with a method, params and an id
Transport: stdioThe host starts the server as a local process and talks over stdin/stdout. Simple, local, no network
Transport: Streamable HTTPThe server runs as a web service; many clients can connect remotely, with authentication
# 1. handshake: agree on protocol version and capabilities → {"jsonrpc":"2.0", "id":1, "method":"initialize", "params":{...}} # 2. discovery: what tools do you have? (the agent learns them at RUNTIME) → {"jsonrpc":"2.0", "id":2, "method":"tools/list"} ← {"jsonrpc":"2.0", "id":2, "result":{"tools":[{"name":"lookup_fact", "description":..., "inputSchema":{...}}]}} # 3. invocation → {"jsonrpc":"2.0", "id":3, "method":"tools/call", "params":{"name":"lookup_fact", "arguments":{"query":"mount everlore"}}} ← {"jsonrpc":"2.0", "id":3, "result":{"content":[{"type":"text", "text":"8,850 meters tall..."}], "isError":false}}
Section 08

MCP in Practice: Server, Client, Agent

A complete MCP server in a few lines (Python SDK, FastMCP)

from mcp.server.fastmcp import FastMCP mcp = FastMCP("knowledge-base") @mcp.tool() def lookup_fact(query: str) -> str: """Look up a fact about a named place or product.""" return KNOWLEDGE_BASE.get(query.lower(), "No matching entry.") @mcp.resource("kb://topics") def topics() -> str: return ", ".join(KNOWLEDGE_BASE) if __name__ == "__main__": mcp.run() # stdio by default; mcp.run(transport="streamable-http") to serve over HTTP

Using it from an agent

# Low level: the official client async with stdio_client(StdioServerParameters(command="python", args=["kb_server.py"])) as (r, w): async with ClientSession(r, w) as session: await session.initialize() tools = await session.list_tools() # discovery result = await session.call_tool("lookup_fact", {"query": "mount everlore"}) # High level: turn every MCP tool into a LangChain tool for a LangGraph agent from langchain_mcp_adapters.client import MultiServerMCPClient client = MultiServerMCPClient({"kb": {"command": "python", "args": ["kb_server.py"], "transport": "stdio"}}) mcp_tools = await client.get_tools() # now usable like any @tool

Agent tool vs. MCP tool

Framework tool (@tool)MCP tool
Where the code runsInside the agent's own processIn a separate server process, local or remote
How the agent knows about itHard-coded in the agent's tool listDiscovered at runtime with tools/list
Reusable by other apps?Only within that frameworkYes: any MCP host (Claude, IDEs, LangGraph, others)
Best forSmall, app-specific helpersShared integrations: databases, GitHub, internal knowledge bases
Security: an MCP server's tool descriptions go straight into the model's context. Connect only to servers you trust, pin their versions, and apply the same tool permissions as Section 06. A malicious description can contain hidden instructions ("tool poisoning").
Hands-on: Lab/2_MCP_Server_and_Tools_Lab.ipynb builds an MCP server and client step by step over real JSON-RPC. The main lab plugs the same server into the multi-agent system.
Section 09

Agent vs. Tool

With tools fully defined, the difference is easy to state: the agent has a goal and decides; the tool has no goal and is called.

Tool
  • No goal of its own
  • Never decides whether to run; always invoked
  • Usually stateless between calls
  • Same input → same output (usually)
Agent
  • Pursues a goal
  • Decides which tool to call, when, and with what arguments (Section 05)
  • Carries state and memory across steps
  • Can behave differently run to run

Where the line blurs: agent-as-tool

A sub-agent can be wrapped as a tool: the main agent calls research(question) like any function, but inside, a whole agent plans and calls its own tools. From the caller's side it is a tool; from the inside it is an agent. The test is always the same: where does the decision-making live?

ToolAgent-as-toolAgent
Own goal?NoYes, given by the callerYes
Decides its own steps?NoYes, internallyYes
Examplecalculator("340/28")research("fuel status of the relay station")The supervisor that called it
Exam favourite: "Is a calculator function passed to an LLM an agent?" No. It is a tool made available to an agent. The LLM deciding when to call it, and holding the goal, is the agent. The distinction is about where the decision lives, not about how complex the code is.
Section 10

Key Takeaways & Exam Prep

✓

A tool = name + description + schema

The description is the model's only guide to using it.

✓

The model never runs tools

It emits a tool call; the harness executes it and returns the result.

✓

Autonomy is set per tool

By reversibility and stakes: auto-run, log, or ask a human.

✓

MCP = write once, use anywhere

Host, client, server; tools, resources, prompts; JSON-RPC over stdio or HTTP.

✓

Agent decides, tool is called

Agent-as-tool is an agent seen from outside as a tool.

Common exam questions

QuestionShort answer
What does a model need to know about a tool, and where does it get it?Name, description and input schema, supplied by the harness with each request; it never sees the implementation
Who executes a tool call?The harness. The model only emits a structured request; the harness runs it and returns the result as a tool message
Name three ways to implement tool selection.Native tool calling, constrained structured output (schema-forced choice), and a dedicated router (classifier or rules)
How should autonomy be set for a "make payment" tool vs. a "search" tool?Search can run automatically (read-only, low stakes); payment needs human approval or should not be given to the agent (irreversible, high stakes)
What problem does MCP solve?The N×M integration problem: without a standard, each framework needs its own connector per tool; with MCP a server works with every compatible host
Name MCP's three server primitives and who controls each.Tools (model), resources (application), prompts (user)
What is the defining difference between an agent and a tool?An agent has a goal and decides which actions to take; a tool has no goal and only runs when invoked
