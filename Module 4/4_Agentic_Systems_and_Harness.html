Agentic Systems & the Agent Harness

Parts 1–3 gave us the pieces: agent types, planning strategies and tools. This Part assembles them. First the types of agentic system: workflows, single agents and multi-agent systems. Then the agent harness, the software around the model that makes any of them run: the loop, tools, memory, state, safety and observability.

Section 01

Types of Agentic Systems

"Agentic system" covers a range. The useful question is: who decides the control flow, your code or the model?

FIG 1 — The spectrum of agentic systems. Start at the left and move right only when the task needs it.
TypeWho decides the stepsUse whenExample
WorkflowYour code, with LLM calls at fixed pointsThe steps are known in advanceExtract fields from an invoice → validate → write to a database
Single agentOne model, choosing tools in a loopThe steps depend on what the tools returnA support assistant that searches docs and checks order status as needed
Multi-agentSeveral agents, coordinated by a supervisor or by handoffsThe task splits into distinct specialities, or needs parallel workA research system: one lead agent and several sub-agents searching in parallel
Rule of thumb (Anthropic, "Building Effective Agents", 2024): find the simplest thing that works. A single well-prompted LLM call with retrieval beats an agent for many tasks; a workflow beats an agent when the path is predictable. Add autonomy only when it pays for its cost and unpredictability.
Section 02

Workflows: Fixed Paths With LLM Steps

Five patterns cover most workflows. Each is a small graph you can draw before writing any code.

PatternShapeExample
Prompt chainingA → B → C, each step's output feeds the next, with checks in betweenOutline → draft → translate a report
RoutingClassify the input, then send it down one specialised branchRefund questions to one prompt, technical issues to another
ParallelisationRun several LLM calls at once and combine them (split the work, or vote)Check one contract against five clauses in parallel
Orchestrator–workersOne LLM breaks the task into sub-tasks at runtime and hands them to workersEdit every file a code change touches
Evaluator–optimizerOne LLM produces, another critiques, repeat until good enough (Part 2's reflection as a workflow)Draft → review against a style guide → revise
The boundary with agents: orchestrator–workers already lets the model decide the sub-tasks, so it sits at the edge of the spectrum. Once a model also decides which tools to call and when to stop, it is an agent.
Section 03

Single-Agent Systems

A single agent is one model, a set of tools and a loop: reason, call a tool, observe, repeat until done. It uses one of Part 2's planning strategies (usually ReAct) and Part 3's tool-calling loop. Most production "agents" are this.

FIG 2 — A single agent: one model loops over its tools until it can answer.
# A complete single agent with LangChain's helper (built on LangGraph); the lab builds the same graph by hand from langchain.agents import create_agent agent = create_agent(model=llm, tools=[lookup_fact, run_python], system_prompt="You answer questions about the course knowledge base.") agent.invoke({"messages": [("user", "How many days of fuel does the relay station have?")]})

When one agent stops being enough

SymptomWhy it happens
It picks the wrong tool more often as you add toolsToo many similar tool descriptions to choose between (Part 3, Section 05)
Its prompt has grown into several jobs at onceInstructions for different specialities conflict
Long tasks run out of contextEvery tool result piles up in one conversation
Independent sub-tasks run one after anotherA single loop can't work on two things in parallel
Section 04

Multi-Agent Systems

A multi-agent system (MAS) is a set of agents, each with its own instructions, tools and goal, that coordinate to complete a task. The idea is classical (Part 1's timeline: FIPA in the 1990s, warehouse robot fleets); LLMs just changed what is inside each agent.

How agents relate: the classical vocabulary

RelationshipMeaningExample
CooperativeShared goal, divided labourResearch, maths and writing agents answering one question
CompetitiveConflicting goalsA negotiation between a buyer agent and a seller agent; debate between agents
HierarchicalA coordinator delegates to specialists and combines their resultsAmazon's warehouse robots under a central task assigner; the supervisor pattern below

Modern architectures

ArchitectureHow control flowsStrengthWeakness
SupervisorOne agent routes each step to a specialist; specialists report back only to itEasy to reason about and debugThe supervisor is a bottleneck and costs an extra call per step
Hierarchical teamsSupervisors of supervisors (a research team, a writing team)Scales to many agentsMore layers, more latency
Network / swarmAny agent can hand off directly to any otherFlexible, no central bottleneckHard to predict and debug
PipelineFixed order: A's output is always B's inputPredictable (really a workflow)No dynamic routing
FIG 3 — A hierarchical MAS: the Supervisor never does the work itself, only decides who does and combines what comes back. This is exactly the structure this module's lab notebook implements in LangGraph.

The supervisor pattern, as LangGraph code

LangGraph models the system as a graph: a shared state object passed between nodes (each an agent or function), with conditional edges deciding what runs next. The supervisor's routing decision is a conditional edge.

from langgraph.graph import StateGraph, END from typing import TypedDict, Literal class AgentState(TypedDict): messages: list # shared conversation so far next: Literal["research", "math", "writer", "FINISH"] def supervisor_node(state: AgentState) -> AgentState: # LLM-as-router (Section 05) — decides who handles this, or whether we're done decision = router_llm.invoke(state["messages"]) return {"next": decision} def research_node(state: AgentState) -> AgentState: result = research_agent.invoke(state["messages"]) # tools: search, RAG (Mod. 3) return {"messages": state["messages"] + [result]} # math_node, writer_node follow the same shape — omitted for brevity graph = StateGraph(AgentState) graph.add_node("supervisor", supervisor_node) graph.add_node("research", research_node) graph.add_node("math", math_node) graph.add_node("writer", writer_node) graph.set_entry_point("supervisor") # the conditional edge IS the routing decision — Section 05's choice, wired into the graph graph.add_conditional_edges( "supervisor", lambda state: state["next"], {"research": "research", "math": "math", "writer": "writer", "FINISH": END}, ) # every specialist reports back to the supervisor — never to each other (hierarchical, not peer-to-peer) for node in ["research", "math", "writer"]: graph.add_edge(node, "supervisor") app = graph.compile()
Real-world example: Anthropic's Research feature (2025) uses a lead agent that plans and spawns several sub-agents to search in parallel, each with its own context. Anthropic reported it beat a single agent by about 90% on its internal research evaluation, while using roughly 15 times more tokens than a normal chat. That is the multi-agent trade-off in one sentence.
When not to go multi-agent: when sub-tasks depend tightly on each other's details. Agents only see what is passed to them, so decisions made in one context can conflict with another's (Cognition, "Don't Build Multi-Agents", 2025). Multi-agent pays off for parallel, separable work; a single agent with good context is often better for tightly coupled tasks like editing one codebase.
Section 05

Routing & Handoffs: How Agents Pass Work

Every multi-agent system needs a rule for who works next. There are two mechanisms.

Routing: a coordinator picks the agent

ApproachHow it decidesTrade-off
LLM-as-routerGive an LLM the request and the agents' descriptions; force the answer into a schema such as Literal["research","math"]Handles new phrasing well; costs a model call; can be inconsistent
ClassifierA small model trained on request → agent labelsFast, cheap, consistent; needs labelled data and retraining
RulesKeywords, regexes or explicit conditionsFully predictable; brittle to unexpected phrasing

Handoffs: an agent passes control itself

In a handoff the current agent decides to transfer the conversation, usually by calling a special tool such as transfer_to_billing_agent. The OpenAI Agents SDK is built around handoffs; in LangGraph a node returns Command(goto="billing", update={...}) to jump to another agent and update the shared state at once.

Routing vs. handoff: routing keeps one agent in charge (supervisor); handoffs let control move between peers (network). Many systems mix them: a supervisor routes, and specialists can hand back when they are done or stuck.
Section 06

The Agent Harness

None of the above happens inside the model. An LLM is stateless: tokens in, tokens out, once. The agent harness is the software around it that turns that single call into a running agent. A finished product such as Claude Code, Cursor or the OpenAI Codex CLI is a model plus a harness.

FIG 4 — The eight responsibilities of an agent harness. Sections 06–08 cover each; the lab builds every one in LangGraph.
#ComponentWhat it doesIn LangGraph
1InstructionsDecides exactly which tokens the model sees: system prompt, role, rulesThe prompt you pass to each agent node
2ToolsHolds the tool schemas, runs the calls the model requests, returns results (Part 3)@tool, bind_tools, ToolNode, MCP adapters
3The loopCalls the model, runs tools, decides when to stop; caps the number of stepsGraph edges; recursion_limit
4Memory & contextWhat is remembered, and how to keep long runs within the context window (Section 07)Checkpointer (short-term), Store (long-term)
5State & checkpointsSaves state after every step so runs can pause, resume or be replayedMemorySaver, SQLite/Postgres savers, thread_id
6Permissions & HITLEnforces Part 3's tool permissions; pauses for human approvalinterrupt() and Command(resume=...)
7Sub-agentsStarts specialists and returns only their result to the parent (Section 04)Sub-graphs as nodes; Command(goto=...)
8ObservabilityLogs every model and tool call; handles errors, retries and timeouts; supports evaluationStreaming, LangSmith tracing

A harness in 20 lines

Stripped of any framework, a harness is a loop. Every framework in Section 09 is a richer version of this:

def run_agent(user_msg, tools, system_prompt, max_steps=8, needs_approval=()): messages = [{"role": "system", "content": system_prompt}, # 1 instructions {"role": "user", "content": user_msg}] for step in range(max_steps): # 3 loop with a hard cap reply = llm(messages, tool_schemas=[t.schema for t in tools]) # the only model call messages.append(reply) if not reply.tool_calls: return reply.content # done for call in reply.tool_calls: # 2 tools: the harness executes if call.name in needs_approval and not ask_human(call): # 6 permissions result = "Denied by user." else: try: result = TOOLS[call.name](**call.args) except Exception as e: result = f"Error: {e}" # errors become observations messages.append({"role": "tool", "tool_call_id": call.id, "content": str(result)}) log(step, call, result) # 8 observability messages = compact_if_too_long(messages) # 4 context management save_checkpoint(messages) # 5 state return "Stopped: step limit reached."
Exam favourite: "Two products use the same LLM. Why can their agents behave completely differently?" Because almost everything that makes an agent useful or safe (which tools exist, what runs without approval, how context is managed, whether sub-agents are used) lives in the harness, not the model.
Section 07

Harness: Memory & Context

The context window is finite and resets between sessions unless the harness persists something. Memory decides what is kept; context management decides how much it costs to keep it.

Memory typeScopeTypical implementationIn LangGraph
Short-term (working)One conversation or taskThe message list in the context windowState + a checkpointer, keyed by thread_id
EpisodicSpecific past attemptsStored reflections (Part 2, Section 10), logs of past runsItems saved in the Store
Long-term (semantic)Across sessions, indefinitelyFacts about the user or domain in a database or vector store (Module 3)The Store, namespaced per user, optionally with embedding search
Memory and RAG are the same mechanism with a different corpus. Module 3's RAG retrieves from documents prepared in advance. Agent memory retrieves from a corpus the agent writes itself: past conversations, decisions and outcomes. Same chunking, embedding and retrieval.

Keeping long runs affordable

TechniqueWhat it doesWhere you meet it
KV-cache reuse (prompt caching)If the start of the prompt (system prompt, tool schemas) is byte-identical to the last call, the model reuses its cached attention state instead of recomputing it, cutting cost and latencyProvider prompt caching (e.g. Anthropic's cache_control)
Compaction (rolling summary)When the transcript nears the limit, older turns are summarised instead of droppedClaude Code's automatic compaction; a LangGraph summarisation node
Sliding windowKeep only the last N turns; discard the restSimplest option; loses information
External scratchpadWrite notes, plans and large results to files or a store, and read back only what is neededAgent "todo" and notes files; the LangGraph Store
Sub-agent isolationA sub-agent works in its own context and returns only a summarySection 04's research example
Why harnesses put stable content first: the KV cache only helps for an unchanged prefix. Change anything early in the prompt and everything after it must be recomputed. So harnesses keep the system prompt and tool definitions fixed at the start, and put the changing conversation at the end.

Section 09

Frameworks for Building Harnesses

Each framework below is a different set of ready-made harness parts. Underneath, almost all do the same thing: describe tools as schemas, let the model emit tool calls, run them, and feed results back. They differ in who controls the loop and what the main abstraction is.

FrameworkCore abstractionBest fit
LangChainChains (fixed pipelines) and Tools (Part 3) — compose prompt → model → parser, with tools as callable objects a model can be pointed atStraightforward pipelines; a large ecosystem of pre-built integrations
LangGraphAn explicit state graph — nodes are steps (including agents), edges define control flow, state is a typed object passed between nodes (Module 3's lab)Multi-step or multi-agent workflows with branches, loops, and conditional routing — this module's lab
DSPySignatures + Modules (Module 2) — declare the transformation, let an optimizer compile the actual prompt/tool-selection logicWhen tool-selection quality itself should be measured and optimized against a metric, not hand-prompted
Google ADK (Agent Development Kit)A framework for building, evaluating, and deploying agents with built-in support for multi-agent orchestration and tool/function schemas, integrated with Google's model ecosystemProduction deployment on Google Cloud infrastructure, native multi-agent orchestration primitives
CrewAIRole-based multi-agent teams — each Agent has a role, goal, and backstory plus a list of tools; Tasks are assigned to agents and a Crew runs them sequentially or under a manager agent. Flows add event-driven, deterministic control around crewsQuickly prototyping "a team of specialists" (researcher → writer → reviewer) where the roles map naturally to the problem
AutoGen / Microsoft Agent FrameworkConversable agents that solve tasks by exchanging messages — tool calls and code execution happen inside a multi-agent conversation (group chat, two-agent chat). Microsoft has since merged AutoGen and Semantic Kernel into the Microsoft Agent FrameworkResearch and enterprise multi-agent systems, especially on Azure / .NET + Python stacks; agents that write and run code
OpenAI Agents SDKA minimal set of primitives — Agents (instructions + tools), handoffs (one agent delegating to another, itself exposed as a tool call), guardrails on input/output, and built-in tracing; successor to the experimental Swarm libraryLightweight agents and handoff-style multi-agent apps on OpenAI models, with little framework overhead
Claude Agent SDKAnthropic's agent harness (the loop behind Claude Code) — the SDK runs the tool loop for you, ships built-in tools (file read/edit, shell, web search), connects external tools via the Model Context Protocol (MCP), and supports subagents, hooks, and permission modesLong-running, tool-heavy agents (coding, research, ops) where file system / shell access and fine-grained permission control matter
LlamaIndexData-centric agents — any index or query engine can be wrapped as a tool (QueryEngineTool, FunctionTool); AgentWorkflow and event-driven Workflows orchestrate one or many agents over that dataAgents whose main job is reasoning over your documents and databases — agentic RAG (Module 3) with many retrieval tools
smolagents (Hugging Face)A deliberately small library whose signature CodeAgent writes its actions as Python code that calls tools as functions, instead of emitting one JSON tool call per step; also has a classic ToolCallingAgentTeaching and experimenting with open-weight models; tasks where composing several tool calls in one code step (loops, variables) beats one-call-per-turn JSON

They combine, and MCP connects them: a common stack is DSPy to optimise a prompt, LangGraph to orchestrate agents, LangChain integrations and MCP servers for tools, served behind an API. Because most frameworks can now consume MCP servers (Part 3), a tool written once works across all of them.
Section 10

End to End: One Request Through the Whole Module

A worked example ties every Part together. Request to a company assistant: "What is the battery capacity of the Zylarian Communicator? Email the summary to the ops lead."

StepWhat happensConcept
1The harness loads the system prompts, the tool schemas and this user's long-term preferences (who "the ops lead" is, how to sign reports)Harness: instructions, memory (Sections 06–07)
2The supervisor makes one structured decision: route = research, wants_email = trueRouting with structured output (Section 05)
3The research agent calls lookup_fact, served by an MCP server: "3,200 mAh battery"Goal-based ReAct agent (Part 2), tools and MCP (Part 3)
4The writer turns the findings into the final answer, with the user's sign-off, and reports back to the supervisorSpecialist pipeline: specialist → writer → supervisor (Section 04)
5The supervisor sees an email was requested. send_report is a high-risk tool, so the harness pauses for approvalTool permissions (Part 3 Section 06), human-in-the-loop (Section 08)
6A person approves; the email is sent; every step was checkpointed and can be replayedState and observability (Section 08)

Section 11

Key Takeaways & Exam Prep

✓

Workflow → single agent → multi-agent

Move right only when the task needs the model to decide the control flow.

✓

Supervisor is the default MAS

One router, specialists report back; handoffs for peer-to-peer.

✓

Multi-agent costs tokens

Worth it for parallel, separable work; not for tightly coupled tasks.

✓

The harness makes the agent

Instructions, tools, loop, memory, state, permissions, sub-agents, observability.

✓

Memory = RAG over your own history

Checkpointer for the thread; Store for the long term.

Common exam questions

QuestionShort answer
What distinguishes a workflow from an agent?In a workflow, code decides the sequence of steps; in an agent, the model decides which tools to call and when to stop
Name four multi-agent architectures.Supervisor, hierarchical teams, network/swarm (handoffs), pipeline
Routing vs. handoff?Routing: a coordinator chooses the next agent. Handoff: the current agent transfers control itself, usually via a transfer tool
When does a multi-agent system beat a single agent, and at what cost?When work splits into parallel, separable parts or needs isolated contexts; it costs many more tokens and adds coordination failures
List the responsibilities of an agent harness.Instructions, tool registry and execution, the loop and its limits, memory and context management, state and checkpointing, permissions and human-in-the-loop, sub-agent orchestration, observability
Short-term vs. long-term memory in LangGraph?Short-term: graph state saved by a checkpointer per thread_id. Long-term: a Store shared across threads, namespaced per user
How does KV-cache reuse reduce cost, and what does it require?Cached attention state is reused for an unchanged prompt prefix, so only new tokens are computed; it requires stable content (system prompt, tools) at the start
