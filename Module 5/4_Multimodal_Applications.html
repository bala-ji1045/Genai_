Section 01

OCR Pipelines

OCR (Optical Character Recognition) extracts machine-readable text from an image — still the workhorse first step in most document pipelines, even alongside full vision-language models (Module 5 Part 2b §01–§06), because it's cheap, fast, and precise for pure text extraction.

StageWhat happens
Layout detectionLocate text regions, tables, columns, headers before reading any characters
Text recognitionConvert each detected region's pixels into character sequences
Post-processingSpell-correction, reading-order reconstruction, confidence scoring
OCR vs. a VLM reading the same document, revisited from Part 1 §02: OCR is precise but blind to non-text content (charts, photos, signatures) and to why layout matters; a VLM understands layout and visual context but can be less precise character-for-character, especially on small or stylized text. Production document pipelines (§05) commonly use both: OCR for exact text, a VLM for everything OCR can't capture.
Section 02

Image Embeddings

Module 5 Part 2a §04–§05 explained how CLIP builds cross-modal embeddings. As an application, this means: run every image in a collection through CLIP's image encoder once, store the resulting vectors, and you have a searchable index — identical in structure to Module 3's text-chunk embeddings.

// Building an image embedding index — directly parallels Module 3 §03's FAISS setup image_embeddings = clip_model.encode_images(all_images) // [n_images, embedding_dim] index = faiss.IndexFlatIP(embedding_dim) index.add(image_embeddings) // Query by TEXT (cross-modal) or by IMAGE (pure visual similarity) — same index, either query type query_vec = clip_model.encode_text(["a red bicycle"]) // or: clip_model.encode_image(query_img) D, I = index.search(query_vec, k=5)
No new infrastructure needed. Everything downstream — FAISS index type choice (Module 3 §03), hybrid retrieval, re-ranking (Module 3 §§06-07) — applies to image embeddings exactly as it applied to text chunks. The only thing that changed is which encoder produced the vectors.
Section 03

Multimodal Retrieval

Multimodal retrieval extends Module 3's semantic search (§02) across modalities: a text query can retrieve images, an image query can retrieve text, and — with a shared index — both at once.

Query typeRetrievesExample
Text → ImageImages matching a text description"Find product photos showing visible stitching damage"
Image → TextText passages relevant to an imageUpload a photo of a rash, retrieve relevant medical documentation
Image → ImageVisually similar images"Find other products that look like this one"
Exam favourite: "How is multimodal retrieval different from running OCR on images and then doing text retrieval?" — OCR-then-text-retrieval only works for images that are mostly text and only matches on textual content; multimodal retrieval (via CLIP-style embeddings) matches on visual meaning directly, working for photos, diagrams, and charts that have little or no text at all.
Section 04

Multimodal RAG

Module 3's RAG pipeline (chunk → embed → retrieve → generate) extends directly: retrieve relevant images (or image+text chunks) alongside or instead of text, and feed them into a vision-language model's context for grounded generation.

FIG 1 — Multimodal RAG is not a new architecture — it's Module 3 §04's index-time / query-time pipeline, with the retrieval step returning images as well as text, and the generation step using a VLM (Module 5 Part 2b §01–§06) instead of a text-only LLM.
Why this matters especially for §05's documents: a scanned technical manual's answer to "what does the wiring diagram show for pin 4?" genuinely requires retrieving the diagram itself, not a lossy text description of it (Module 5 Part 1 §02) — multimodal RAG is what makes that retrieval possible at all.
Section 05

Document Intelligence & PDF Intelligence Systems

A PDF is not one modality — it's a mix of text, tables, images, and layout, often as a raster scan with no underlying text layer at all. Document intelligence systems combine §01's OCR, layout detection, and VLM understanding to extract structured, queryable information from documents like these.

Pipeline stageTechnique used
Page renderingConvert each PDF page to an image (needed even for "digital" PDFs, to handle scanned pages uniformly)
Layout & table detectionLocate structural regions before extracting content from them
Text extractionOCR (§01) for scanned regions; native text extraction for digital-text PDFs
Chunking & embeddingModule 3 §05's chunking, applied per detected region rather than blindly by character count
Indexing & retrievalModule 3's FAISS pipeline, extended per §03-§04 to include image regions
Exam favourite: "Why does document intelligence chunk by detected layout region rather than by fixed character count (Module 3 §05)?" — a fixed-size chunker has no notion of "this text belongs to this table" or "this caption belongs to this figure," and can silently split a table's header from its rows, corrupting retrieval. Layout-aware chunking respects the document's actual structure, at the cost of a more complex pipeline.
Section 06

Image Captioning

Image captioning — generating a natural-language description of an image — is the most direct application of a VLM's generation capability (Module 5 Part 2b §01–§06), and the task where Part 3's hallucination and evaluation challenges are most visible.

Captioning styleOutputUse case
Generic"A dog running on a beach"Alt-text generation, accessibility
Dense/detailedMulti-sentence description covering multiple objects and relationshipsContent indexing, search
Instruction-conditioned"Describe only the safety hazards visible in this image"Domain-specific extraction (Module 5 Part 4's enterprise use cases)
Connects directly to Part 3 §03: a captioning system deployed in production needs some mitigation for hallucination — commonly, cross-checking generated claims against object-detection output, or explicitly prompting the VLM to only describe high-confidence visual elements — since an unverified caption can silently introduce false information into every downstream system that trusts it (search indexes, accessibility tools, automated reports).
Section 07

Enterprise Multimodal Applications

Where all of the above compose into real systems:

1

Invoice & receipt processing

OCR + layout detection + structured field extraction — §01 + §05, output as structured data.

2

Compliance document review

Multimodal RAG (§04) over scanned contracts and regulations, with faithfulness-checked answers.

3

Visual product search

Image-to-image and text-to-image retrieval (§03) over a product catalog.

4

Automated quality inspection

VLM-based visual reasoning over photos, flagging anomalies for human review (Module 4 Part 3 §06's autonomy spectrum applies directly).

The throughline across all four: none of these introduce a genuinely new technique — each is a specific composition of OCR, cross-modal embeddings, multimodal RAG, and VLM generation, chosen and combined for a concrete business process. This module's lab notebook builds exactly this kind of composition: a multimodal PDF and image QA system.
Section 08

Key Takeaways & Exam Prep

✓

OCR and VLMs are complementary, not competing

OCR for precise text; VLMs for layout, visual context, and non-text content.

✓

Image embeddings reuse Module 3's infrastructure unchanged

Same FAISS pipeline, different encoder.

✓

Multimodal RAG grounds generation in retrieved images, not just text

Essential when the answer genuinely lives in a diagram or photo.

✓

Document intelligence chunks by layout, not character count

Preserves table/figure structure that fixed-size chunking would corrupt.

✓

Enterprise systems compose these pieces, not invent new ones

Invoice processing, compliance review, visual search — all recombinations of §01-§06.

Common exam questions

QuestionShort answer
Why do production document pipelines often use both OCR and a VLM?OCR gives precise text extraction but is blind to layout meaning and non-text content; a VLM understands visual context and layout but is less precise character-for-character — combining both covers each one's blind spot
What changes, structurally, going from Module 3's text RAG to multimodal RAG?The retrieval step can return images as well as text chunks, and the generation step uses a vision-language model instead of a text-only LLM — the overall index-time/query-time pipeline structure is unchanged
Why does document intelligence use layout-aware chunking rather than fixed-size chunking?Fixed-size chunking has no notion of table/figure boundaries and can split structurally related content (e.g. a table header from its rows) across chunks, corrupting retrieval
