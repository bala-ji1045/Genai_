Section 01

LangSmith

Module 4 Part 4's agent architectures involve many chained LLM calls, tool invocations, and routing decisions (the Supervisor pattern, Part 4 §04). When something goes wrong, "which step failed, and why" is genuinely hard to answer without tooling. LangSmith is a tracing and observability platform built for exactly this — every call in a LangChain/LangGraph pipeline (Module 4 Part 3 §04) is automatically logged as a structured trace.

# Tracing is often just an environment variable away for LangChain/LangGraph pipelines import os os.environ["LANGCHAIN_TRACING_V2"] = "true" os.environ["LANGCHAIN_API_KEY"] = "..." # Every chain/agent run in this session now appears in LangSmith as a full trace: # prompt in -> each LLM call -> each tool call -> final output, with latency and cost per step
What a trace showsWhy it matters
Exact prompt sent to the LLM at each stepDebugging "why did the model do that" without guessing at what it actually saw
Each tool call's arguments and return valueDiagnosing tool abuse (Module 6 Part 2 §05) or a mis-routed decision (Module 4 Part 3 §05) after the fact
Per-step latency and token costFinding the actual bottleneck in a multi-agent pipeline (Module 4 Part 4 §04), not guessing
Why this matters specifically for agentic systems: Module 4's multi-agent supervisor pattern means a single user request can trigger many LLM calls across several specialist agents (Module 4's lab notebook). Without tracing, debugging a wrong final answer means re-running the whole pipeline with print statements; with tracing, you inspect the exact recorded path the request actually took.
Section 02

Observability

Observability generalizes LangSmith's tracing (SS01) into the full discipline of understanding a running system's internal state from its external outputs — logs, metrics, and traces, the three pillars carried over from general software observability practice and adapted for GenAI's specific failure modes.

PillarWhat it captures for a GenAI system
LogsEvery request/response pair, tool call, retrieval result — the raw record of what happened
MetricsAggregate numbers over time: latency percentiles, token cost per request, RAGAS scores (Module 6 Part 1 §04) tracked continuously in production, not just at evaluation time
TracesThe full step-by-step path one specific request took (SS01's LangSmith traces are exactly this)
FIG 1 — Evaluation (Part 1) answers "is this good enough to ship"; observability answers "is it still good, right now, on real traffic" — the same metrics, applied at a different cadence and to different data.
Exam favourite: "If a RAG system passed RAGAS evaluation before launch, why would you still need observability?" — evaluation runs against a fixed held-out test set that may not reflect the actual distribution of live user queries, and that distribution can drift over time (Module 3 §10's knowledge-freshness problem is one specific cause). Observability is what detects that drift in production, which offline evaluation structurally cannot see.
Section 03

Serving LLMs — vLLM

Module 1 Part 4 §05's KV cache explained why naive token-by-token generation is wasteful. At production scale — many concurrent users, not one notebook cell — a further problem appears: requests arrive at different times with different lengths, and naively serving them one at a time (or in fixed batches) wastes enormous GPU capacity. vLLM is an inference-serving engine built specifically to solve this.

vLLM techniqueProblem it solves
PagedAttentionStandard KV cache allocation reserves a fixed contiguous memory block per sequence, wasting memory on unused space; PagedAttention manages the KV cache in fixed-size, non-contiguous "pages" (directly analogous to OS virtual memory paging), eliminating that waste
Continuous batchingInstead of waiting for a fixed batch to fully finish before starting the next, new requests join an in-flight batch as soon as a GPU slot frees up — no request has to wait for the slowest one in its batch to finish
Efficient KV cache sharingRequests sharing a common prefix (e.g. the same system prompt, Module 6 Part 2 §04) can share the same cached computation instead of recomputing it per request
Why this matters at the scale this course has been building toward: Module 4's multi-agent systems and Module 3's RAG pipelines both mean many LLM calls per user request. A serving layer that wastes GPU memory or serializes requests unnecessarily multiplies that cost directly — vLLM-style serving is what makes agentic and RAG-heavy architectures economically viable at real user volume, not just functionally correct in a single-user notebook.
Section 04

The Rest of the Production Stack

The remaining tools this module names complete the path from a notebook to a deployed, usable system:

ToolRole
FastAPIWraps the GenAI pipeline (RAG, an agent, whatever this module's lab evaluates) behind an HTTP API — the standard interface other systems and frontends call
StreamlitRapid UI construction for internal tools, demos, and evaluation dashboards — often the fastest path from "a working pipeline" to "something a non-engineer can click through"
DockerPackages the application (code, dependencies, model weights or serving config) into a reproducible container — the same environment runs identically in development and production
OllamaRuns open-weight LLMs locally with a simple interface — useful for development, cost-controlled prototyping, or fully on-premises deployment without a cloud API

Section 05

Key Takeaways & Exam Prep

✓

Tracing debugs multi-step pipelines

LangSmith records the exact prompt, tool call, and output at every step — essential once agents chain many calls.

✓

Observability is continuous; evaluation is periodic

The same metrics, applied to live traffic instead of a fixed test set, catch drift evaluation structurally can't see.

✓

vLLM solves memory waste and serialized requests

PagedAttention and continuous batching make concurrent LLM serving actually efficient.

✓

The rest of the stack turns a pipeline into a product

FastAPI for the API, Streamlit for the UI, Docker for reproducibility, Ollama for local/on-prem serving.
